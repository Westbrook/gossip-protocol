# Candidate observations and product-purpose admission (C06)

This integration connects newly executed, source-bound CLI and HTTP histories to
`project_acceptance_registry_v1.Observation`. It is an acceptance adapter for
declared slices. It does not supply a production ScopePlan, qualification
authority, promotion authority, or the cumulative study controller.

The historical CLI v4 and HTTP v3 qualification protocols and journals remain
unchanged. A qualification result cannot be renamed into a public release,
independent acceptance, or repeatability result. Each new purpose is registered
before a fresh execution. Reading an existing original again verifies that
original; it does not create another sample or independent repeat.

## Concrete path

1. Capture the complete Git source and construct a prospective, versioned
   CLI v5 or HTTP v4 binding and product gate.
2. Authenticate that registration through a separately owned controller
   capability. The new protocols share one canonical source inventory identity.
3. For independent acceptance and repeatability, authenticate the complete
   irreversible six-trajectory cohort freeze, including the exact subject's
   source, milestone, requirements and execution contract. Recheck it before
   dispatch, after execution and during observation.
4. Retain one durable intent, original process/wire journals, and external
   checkpoints. An interrupted intent cannot dispatch again.
5. Reconstruct observations and publish a host verifier receipt. The concrete
   source checks original registration, exact gate, checkpoint and freeze before
   returning a Registry observation. Candidate verdict dictionaries have no
   acceptance entry point.

`candidate_observation_admission_v1` defines the shared admission boundary.
`candidate_client_execution_v5` and `candidate_http_execution_v4` own the new
physical journals. `candidate_client_observation_source_v1` and
`candidate_http_observation_source_v1` provide the concrete observation sources.
The new `candidate_http_observation_v2` reconstructs raw Engine requests,
inspections, process completion, multiplexed streams, server epochs and product
HTTP facts from an exact v4 owner and its retained checkpoint.

The supplied registration and cohort callbacks are trusted host capabilities.
Matching dataclasses, hashes, or success callbacks do not themselves establish
that authority. Tests using authored callbacks qualify boundary mechanics only.
The full production controller must authenticate its own durable originals,
external checkpoints, slot admission, and global prohibition of further model
work. This integration does not manufacture those proofs.

## Preserve the complete denominator

The CLI profile retains the original 57 history definitions, 305 command steps,
and 900 assertion cells. All 32 normatively unspecified cells remain explicit;
they are not scored as passes. Each history gate exposes its complete ordered
assertion roster. Known false assertions remain failed alongside unavailable
or unentered sibling assertions.

An HTTP gate retains its whole literal history, with one Registry outcome per
step and a complete per-facet diagnostic roster in the verifier. This keeps
long histories within the Registry's item bound without dropping requests,
CLI steps, lifecycle actions, relations, or assertions. A step passes only when
its applicable mandatory facets pass. Failed applicable facets dominate unknown
siblings; unentered steps remain unavailable. Normatively unspecified facets
remain diagnostics and cannot supply missing mandatory coverage.

State-dependent expectations require their declared prerequisites. A mismatching
body is not attributed to the product when the expected prior state is unproven.
Independently known failures, such as an incorrect status or a natural finite
CLI exit, survive unrelated missing evidence. A natural CLI exit can remain
known after a later keeper/state check fails; its output semantics remain
unavailable. Exit zero alone never restores a complete step pass.

An incomplete intended request does not provide a response verdict for that
complete request. A final HTTP status after a fully sent request can remain
known even when the response body is incomplete. Raw listener observations
retain their own eligibility and coverage limitations.

Authority failures are translated into the scope consumer's structured invalid
or unavailable results. They do not abort aggregation and erase an earlier
known product failure.

## Scope and scientific limits

These profiles prospectively reuse authored qualification definitions and
semantics, with their authoring provenance disclosed. A fresh execution after a
freeze does not make that corpus held out or source blind. Separate independent
project-family confirmation remains required for scientific conclusions.

The CLI roster does not cover every B03 obligation. The full HTTP catalog has
276 histories; the small adapter qualification roster is not execution of that
catalog. Browser journeys, remaining storage/concurrency/recovery/release
obligations, the complete acceptance authorities, and the four-milestone,
six-trajectory controller still require implementation or qualification.
Existing release v2 retains its historical source-hash domain; integrating it
into the common production subject needs explicit, verified identity mapping.

New physical controls cover CLI public success, independent persistent history,
and repeatability with a known wrong exit followed by a hang; HTTP public
health, independent body-defect detection, and a mixed CLI/restart history.
These are engineering qualification fixtures, not live model comparisons.
Their execution and independent raw audit must be recorded separately from
passing offline tests. No provider work or new statistical sample is implied.

## Verification

Every new test class is registered in `verification-manifest.json`. The central
verifier runs static checks before the selected offline tests. Concrete observation
sources check both registered file identities and source-declared functions in
already loaded evaluator modules; matching files on disk alone cannot certify a
stale imported evaluator. These checks execute no candidate source. Physical
qualification still requires a fresh worker under an exact source freeze.
Function comparison is not attestation of arbitrary interpreter state or
mutated globals, import-time defaults, or decorator state, and it does not replace
that launch prerequisite. Physical classes
use the explicit Docker lane only after the offline gate passes, with separate
owned journals and bounded resources. The currently running HTTP v3 experiment
continues against its frozen checkout; the new development checkout does not
change those inputs. Original failures and audit corrections remain retained.

## Retained checkpoint

The final combined static gate and all **149 selected offline checks** passed in
12 fresh class workers, with no reused classes, skips, source drift or runtime
drift. Elapsed verification time was 78.66 seconds; this is development
verification time, not an agent-policy benchmark. The preceding 137-check gate
is retained but superseded after the loaded-source checks and exception mapping
changed.

The [machine-readable checkpoint](../analysis/candidate-observation-admission-v1-checkpoint.json)
records exact source hashes, class receipts and the remaining work. All six new
Docker controls remain **unexecuted**. Separately, 14 of the original HTTP v3
experiment’s 20 methods have passed scoped independent raw audits; that frozen
experiment is still running at this checkpoint. No new provider calls or
comparative trajectories were made in this cycle.
