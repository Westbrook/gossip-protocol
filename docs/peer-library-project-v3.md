# A twenty-role project integration rehearsal

The first larger swarm observation established twenty independently running role
processes, continuous gossip during worker calls, durable call accounting and
sixteen private Git proposals. It did not establish project completion. This
next integration joins those mechanisms to a real software change: durable,
cancelable ingestion for the Local Research Library.

The rehearsal uses sixteen builders, four per package, and four reviewers. The
packages are catalog, ingestion, query and clients. One of the four reviewers
also selects candidates, consuming a separate recorded action. Deterministic
transport, financial accounting, evidence verification and Git release services
are infrastructure; they are not additional model agents.

This qualification has a trusted controller issuing a fixed sequence of role
directives. Evidence travels through the gossip meshes, but task discovery and
the decision to start the repair are scripted. A successful run therefore
cannot establish decentralized planning or a gossip advantage over centralized
orchestration.

## The project and its deliberate failure

The checked-in authored reference implements durable SQLite jobs, generation
fences, atomic commits and rollback, bounded directory/ZIP/JSON intake, API
operations, CLI commands and browser job controls. The seed, public requirements
and independent transition oracle remain unchanged. Reference source is a
trusted response fixture for this offline rehearsal; it must never be inserted
into a future live builder's input as if the model had produced it.

The initial catalog candidate intentionally confuses shared content storage
with document identity. Two files with identical content should share one blob
while retaining two documents and their source paths. The defective catalog
collapses those documents. Its Git merge is clean, but the frozen public
`m1-per-source-provenance` check must fail on the combined application.

The sixteen proposals are independently published scripted artifacts, mostly
copies of the same good reference within each package. The selector deliberately
chooses the defective B01 catalog proposal to exercise rejection and repair.
This is not a sample of sixteen independently conceived designs or evidence
that a reviewer can identify the best of many implementations.

The intended sequence is:

1. Builders publish actual scoped commits and Git bundles from private stores.
2. A receiver verifies those bundles against the exact accounted requests and
   results, and publishes the complete eligible candidate frontier.
3. A recorded selector action chooses four contributions. Structural staging
   merges them without advancing the protected branch.
4. The actual merged source executes in the pinned Docker sandbox. Reviewers
   receive that target, source and execution evidence through their own meshes,
   and return retained rejection artifacts. Release remains blocked.
5. A new catalog generation repairs the failed combined source. Unchanged
   packages retain their original generation and evidence. The same role
   journals continue to enforce aggregate call limits.
6. Selection, sandbox evaluation and all eight scoped approvals refer to the
   new exact target. Only the release gate can authorize the protected Git
   compare-and-swap.

## What each adapter proves

| Adapter | Evidence it owns | Important limit |
| --- | --- | --- |
| Project views | Complete, locally arrived source and evidence bytes reconstructed against the actual worker request | A self-reported recipe does not authorize its instructions, policy or contributions; trusted registration supplies those checks. |
| Project evidence registry | Imported Git files match settled edits, registered base, package scope, instruction template and complete candidate frontier | It verifies contributions and selector outputs; it does not execute source or approve a release. |
| Project execution | Original sandbox receipt bound to exact commit/tree/files, ordered whole assertions, image, runtime, limits and purpose | Fixture execution cannot authorize release. Ambiguous execution intent is retained without automatic reexecution. |
| Project promotion | Monotonic required checks, retained refutations, current registered review responses and durable fenced Git promotion | Public release is not independent final acceptance. Structural staging is not a correctness test. |

Normalized candidate records and complete package-owned source artifacts are
published by the verifying service under its own identity. The original builder
notice and bundle remain retained. Review verification must check both byte
materialization and the registry's exact authenticated contribution references;
matching a contribution's claimed hash alone is insufficient.

Review requests are registered before dispatch. Starting a newer review round
invalidates the previous response for that reviewer, so a delayed old approval
cannot replace a newer rejection. Corrected targets require fresh reviews.

## Qualification and limits

The second physical rehearsal completed in **1,058.79 seconds** including
cleanup (17.65 minutes), under its declared 1,800-second deadline. Its retained
receipt records twenty distinct role processes, 27 settled scripted calls,
seventeen distinct candidate versions, two actual Docker evaluations, eight
rejections followed by eight fresh approvals, and one protected release. All
twenty processes exited successfully; there were no cleanup errors or unsettled
calls, and no provider requests or API spend.

The defective merged target passed seven of eight public histories; only
per-source provenance failed. The repaired target passed all eight in a new
physical evaluation. A separate textual conflict was rejected without changing
its protected head. The initial frontier required sixteen receiver imports;
the repair frontier required thirteen, including twelve unchanged contributions.
Those 29 receiver imports and one private repair-base import must not be counted
as thirty independently created candidate versions.

These timings describe this scripted engineering run. They are neither a live
model speed estimate nor a comparison with four-role or orchestrated execution.
The [durable checkpoint](../analysis/peer-library-project-v3-checkpoint.json)
binds the qualification, original run records, independent audit and source
identities. Public release remains distinct from independent final acceptance.

The first physical attempt reached twenty role processes, sixteen imported
candidate bundles and seventeen settled scripted calls, then stopped before
candidate evaluation. A valid large selector request passed admission but
exceeded a smaller default parser limit during terminal journal verification.
The authority failed closed without invoking the selector again. The original
failed cohort and its valid result/settlement remain retained; correcting this
implementation defect requires fresh qualification and a new execution contract.

The correction compares the canonical retained request envelope directly with
the expected envelope. It avoids parsing the authority's own escaped JSON under
a smaller wire limit and preserves exact scalar types. Request admission limits
have not increased. Regressions cover large ASCII requests, Unicode and control
characters whose journal encoding expands, exact replay after reopen, type
tampering, and rejection before invocation for oversized or malformed input.

The final affected gate physically ran **203 tests** across eleven isolated
class workers: 106 fast, 24 reference-fixture and 73 Git checks. All passed, with
no reused classes, unexpected skips or source/runtime drift. The static gate
passed first; its explicit incremental type coverage is not a claim that every
legacy dynamic function is type-safe. The earlier 157-test gate and the
interrupted superseded-fix gate remain retained as separate observations.

The central verifier runs syntax/type/configuration checks before the affected
offline classes. Authored-reference host smokes and simulated executor tests
remain distinct from actual candidate sandbox execution. A new complete
process-and-project observation is required for the changed execution contract;
the earlier plumbing receipt remains valid historical evidence at its original
source revision.

The present repair path supports a single changed package based on the failed
combined stage. Unchanged packages are integrated before that repair so their
ancestry does not appear as an out-of-scope change. Multiple packages repaired
independently from the same failed combined stage need an additional integration
design: each repair can otherwise import another package's history and correctly
fail the existing scope gate. That gate must not be weakened to make the test
pass.

A useful next design is to keep each repair on its package's topic history and
provide the failed combined tree as explicit review/test context. A new staging
round can then merge the repaired topics together. That needs its own contract
for patch base versus integration context, plus tests for two simultaneous
repairs; it is a proposed extension, not a capability established here.

Even a successful rehearsal establishes only this integrated path with authored
responses. It does not show that models discover the defect, select the best
implementation, persist through the full fault schedule, or outperform an
orchestrator. Real HTTP/browser acceptance, broader multi-package repair and
combined restart/partition recovery require their own evidence.

The shortest useful live follow-up is a separately registered, healthy M1
developmental pilot with sixteen live builders and four live reviewers under
the current central scheduler. It would measure implementation diversity,
review and bounded repair using gossip delivery, without claiming peer-local
planning. It needs an explicitly qualified live financial adapter, real public
task/schema prompts, and outcome-driven selection and repair instead of the
authored success script. A finite budget or deadline termination is an outcome
to retain, not permission to retry until completion.

Capacity must be checked before that pilot: the authored sixteen-candidate
selector already carries roughly 394 KB against a 512 KB record limit. Larger
model implementations and substantive prompts need declared admission bounds
or a qualified bounded retrieval/selection design. Silent truncation would
invalidate the evidence. Freeze model profiles, aggregate allowances, public
feedback and independent post-freeze acceptance before allocating live funds;
this offline rehearsal grants no new spending allowance.

The full [project study](large-swarm-project-plan-v1.md) still has four milestones,
three approaches and healthy/recovery trajectories. Matched decision-placement
and transport comparisons, followed by untouched project families, remain
necessary before a general quality or ranking claim. Completion, inherited
correctness and retained progress after faults are primary; elapsed time, call
cost, queueing and transport volume explain those outcomes.
