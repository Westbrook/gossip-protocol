# Complete prospective C03 HTTP literal catalog, version 1

`gossip_harness/candidate_http_cases_v1.py` materializes every one of the retained
276 rows in their original ten-family order. The shared core and six family
modules construct immutable literal requests, owned input fixtures, source-derived
public expectations and complete ordered process histories. They perform no
candidate/reference execution, provider call, database work, staging or dispatch.
The definition is permanently marked `dispatch_authority=false`,
`acceptance_authority=false`, `fresh_execution=false`, `product_verdict=not_evaluated`.

This completes literal materialization for R05; it does **not** close predispatch
registration, executable recipe qualification, or any P01–P10 acceptance
prerequisite. A declaration hash proves value identity, not that its bytes were
registered before an observation. The eight HTTP target labels and separately
labeled interactions do not reduce the full cumulative acceptance denominator.

## Closed declaration and expectation boundaries

`LiteralCase`, `Step`, `Fixture`, `HttpRequest`, `HttpExpectation` and `Dependency`
are frozen. Each case closes its lifecycle and rejects duplicate steps,
undeclared root directories, cross-epoch requests, live-server CLI handoffs,
unsafe/unbound links, malformed relation descriptors, unknown prerequisite
facets, later prerequisites and raw-only prerequisites with absent facets.
Data fixture path bounds deliberately differ from product source-key bounds,
so the fixture layer can represent inputs rejected at 257 bytes or 17 segments.
Every parent directory is explicit. Raw link target traversal must visit only
explicit regular owned fixtures; lexical normalization alone cannot conceal a
symlink followed by `..`. A declared link is still not proof of staging,
`lstat`/`readlink` verification, or that no forbidden read occurred.

`HttpExpectation` has exactly one mode:

- Pure semantic expectation: fixed supported status/code/body, or an explicitly
  unspecified wrapper/code facet.
- `candidate-http-relations-v1` jobs declaration: exact known six-field jobs,
  except failed `JOB.error` values explicitly related to a named earlier error
  response. Records round-trip through `JobsExpectation`, `JobRule` and
  `ErrorReference`; at least one relation is required and conflicting statuses
  for the same source are rejected. No observed value becomes an expected value.
- Raw facts only: root `GET /` records literal response/listener facts without
  inventing API JSON, status200, MIME, markup, accessibility or browser success.

For prerequisite mapping, `content_requires` conditions the semantic
`body_shape_value` facet, or the relations module's jobs `body_shape_value` facet.
Status and JSON syntax remain independent. Allowed source facets are exactly
`status`, `json_syntax`, `body_shape_value`; a raw-facts-only step has none.
The per-job `error_code_equality` relation remains separately named by its source
error response and subject job, with its own availability; it is not renamed to
an invented generic jobs facet. The declaration records dependencies but performs
no diagnostic propagation or authentication. A qualified bridge must preserve
those facet distinctions and prerequisite attribution.

Success wrappers for HTTP import, submit, single-job reads and actions remain
unspecified. Their supported effects are checked through independent public
censuses. Unknown exact codes stay unclassified; no wildcard learned from a
candidate is substituted. Direct nested ENTRIES extras and bool/float epoch
coercion acquire no invented classification. Root/path lexical cases with
multiple defects do not assert an unspecified precedence. The reviewed norms
refine only the source-supported namespace-parent cases to `invalid_source`.

## Persistent lineage and finite CLI handoff

All history steps declare the same candidate source, database
`/tmp/catalog.sqlite`, owned volume and continuously running owned keeper.
Each server epoch declares its exact argv/root; stop/remove must precede its
successor. Root-change cases stage separate roots with distinct immutable bytes.
Each HTTP request demands both IPv4/IPv6 listener tables at the connected and
post-observation phases, bound to the actual source/server epoch. These are
requirements for future evidence, not assertions that a live listener was seen.

The 29 finite CLI steps occur only after the HTTP server has stopped. Each step
retains literal argv and immutable `cli_state_json` before/after snapshots of
jobs, all document records and export, including the cancelled epoch-two to
queued/running/completed epoch-three progression. Read steps preserve identical
snapshots. The snapshots are inert source-derived values; they prescribe no
invented CLI stdout wrapper. Exit0 and one complete JSON value are recorded
separately. A future authorized CLI bridge must qualify how its actual output
exposes the relevant semantic value and authenticate the same DB/source/keeper
lineage. The final HTTP census cannot substitute for missing intermediate CLI
evidence. No pending CLI v4 approval file is installed or recreated here.

Public jobs/documents/export conservation is distinct from storage conservation
and atomicity. These declarations cannot prove hidden blobs, canonical manifests,
receipt identity, SQLite transaction boundaries, concurrent writers, internal
source delegation or offline rollback. Method receipt replay, store audits,
combined-source integration and browser/delivery obligations remain separate.
