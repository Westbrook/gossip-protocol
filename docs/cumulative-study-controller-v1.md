# Cumulative comparison controller v1

The controller composes the larger comparison as six ordered trajectories, each with four cumulative software milestones. It supplies real role-process, gossip, private Git, integration and financial wiring. It currently returns **acceptance unavailable**: successful public development and a closed spending ledger cannot certify the product.

## What is compared

| Arm | Builders | Reviewers | Task admission |
| --- | ---: | ---: | --- |
| S4-G | 4 | 4 | Peer-local |
| S16-G | 16 | 4 | Peer-local |
| O16-G | 16 | 4 | Durable central scheduler |

Each arm has a healthy and a compound-recovery trajectory. All arms use the same gossip transport, four package boundaries, staged requirements, public evaluation and four executor slots. The cohort contains 96 distinct role identities across six sequential children; it does not launch 96 concurrent agents. More roles do not silently multiply the shared executor capacity.

This design tests builder-pool size and the location of admission decisions under one transport. It does not test emergent decomposition, unrestricted work stealing, or gossip versus a different transport. The separate placement-by-transport study remains necessary. Fixed package boundaries also limit which distributed-Git conflicts this comparison can expose.

## Actual execution path

`cumulative_study_controller_v1` freezes the ordered cohort, releases, runtime limits and source closure. `cumulative_study_runtime_v1` connects original ledger admission, actual role subprocesses, authenticated mesh payloads, private actor repositories, scoped proposals, reviewer selection and protected Git integration. `cumulative_study_role_v1` implements peer-local or centrally assigned work using the same role loop and financial RPC.

Every milestone retains build and review originals, integration outcomes and cumulative public evaluation. A bounded subsequent generation receives the previous public feedback. An unknown effect is retained and never silently redispatched. An exception or deadline stop does not become a successful milestone; the public result that finished after the deadline remains available without completion credit.

The runtime binds the ledger identity before admission and requires fresh protected-Git initialization from the prospective source. Its process-evidence owner records actual launch, ready, exit and stop observations. Before financial sealing it reauthenticates process closure and protected source. Writers stop before original-file census. All six original financial seals and the global barrier precede final evaluation.

The current acceptance implementation is deliberately `UnavailableAcceptance`. A successor must bind the actual complete reviewed scope, final source, independent observations, promotion history and repeatability. Arbitrary injected acceptance booleans cannot grant success. There is no credential-discovery or live CLI in this controller.

## Recovery intervention

The compound trajectory partitions B01's peer links before initial build work or central assignment publication. All peer acknowledgments must report the exact blocked set. Healing requires both the complete initial publication frontier and the minimum declared interval. The runtime retains actual start, publication and end observations.

**Realized partition durations can differ between arms.** This is a matched event-boundary intervention with a minimum duration, not an equal fixed wall-time outage. Comparisons must retain that distinction rather than attributing every recovery difference to placement.

B01 also exits after a known completed financial result and before publishing its role result, then restarts on the same role ports using durable originals. This builder-agent restart is separate from testing a generated application's worker crash recovery. Controller-crash adoption of an active Popen or preexisting protected repository is unsupported; only already completed children can be resumed through their authenticated terminal evidence.
