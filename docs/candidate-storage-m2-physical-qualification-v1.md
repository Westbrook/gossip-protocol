## Independent source review before dispatch

Run `python -B -m tests.candidate_storage_m2_physical_v1 NEW_DIRECTORY` to prepare
six deterministic Git repositories, all source bytes, full manifests, literal
mutations, fixed authored SQLite DDL/schema, exact plans/requests and selector
catalogs. The preparation never dispatches a candidate or supplies approval.
Each output is exclusive; preserve incomplete attempts. Parsing generated
candidate Python as AST data is allowed; importing it into the host is not.

An independent reviewer must inspect the actual candidate bytes, the complete
layout and invocation for each exact request. Their actual report and delivery
originals are supplied separately; the tests never manufacture approvals. The
controller pins an index using `GOSSIP_STORAGE_M2_REVIEW_PACKAGE` and
`GOSSIP_STORAGE_M2_REVIEW_SHA256`. Its shape is:

```json
{"protocol":"candidate-storage-m2-physical-qualification-v1","scope":"actual authored source/layout qualification only","controls":[{"id":"P01","reviewer_id":"REVIEWER","request_sha256":"SHA256","report_sha256":"SHA256","delivery_sha256":"SHA256"}]}
```

The controls array contains all six entries in the table order. Each entry has
`ID/request.json`, `ID/report.json` and `ID/delivery.json` beside the index.
Reports/deliveries follow the existing StorageReviewAuthority/M2ReviewAuthority
exact schemas. Original review bytes enter an independent ExternalHead-protected
checkpoint journal before owner construction; actual freshly captured Git bytes
must match the request. Package hashes authenticate retained bytes; independent
reviewer identity and adequacy remain the trusted controller's responsibility.
These are layout/slice reviews, not complete 312-unit semantic approvals.

The controller registration is explicitly a qualification-only public_release
registration. It cannot establish a completed study trajectory, a frozen
scientific cohort or final cumulative scope authority. The six physical histories
have distinct repetition IDs, journals, owned volumes, containers and purposes
bound through their actual registrations. The three positives may share immutable
source bytes; they do not share a candidate process or observation execution.

has its authentic registration revoked before execute_once. No intent, cleanup

removed. The checkpoint owner protects the external head throughout.

## Execution and resources

Root is the verification and physical-execution owner. Only the explicit Docker
lane runs these classes, after static/offline checks, independent source review
and the final evaluator closure. Missing review configuration fails before even
a read-only Engine call. Candidate deadlines remain the existing policy values;
batch source capture stays fresh at every existing boundary, with the exact
60-second whole-capture deadline and 5-second cleanup allowance. No cached source
snapshot substitutes for a boundary capture.

Each physical class has weight 4, reserving the default runner budget for one
history. Nested work is one container and owned tmpfs volume, one persistent
Docker exec/session with two stream-reader threads, serial control/Git children
with bounded capture readers, journal durability operations and an independent
cleanup evidence channel in the same host process. Up to four stream-reader
threads coexist while a finite control command overlaps the persistent session. M2 action 0 additionally runs two
candidate threads within that same container and its existing CPU/PID/memory
limits; there is no outer case pool. P01's extra attempts/readers are sequential.
The existing 2400-second runner guard is preserved; it does not enlarge any
candidate command, phase, source-capture or cleanup deadline. It is an independent
outer safety bound, not a runtime forecast or a proof every serial maximum fits.
Root may serialize all six classes. A worker timeout is infrastructure failure;
cleanup stays unknown unless authenticated absence proves completion. This
same-process cleanup channel is not a surviving external watchdog.

The owner keeper command has a fixed 1800-second sleep. Each phase response has
30 seconds. A finite Docker command has 30 seconds plus at most 5 seconds for
kill/reap and two 5-second reader joins; session finish has the same 30+5+10
allowances. Runtime identity has 15 seconds. Emergency cleanup has a 120-second
total and 5-second requests. A normal N-phase owner has 7 setup commands, 4N
pause/inspect/copy/unpause commands and 5 cleanup commands: 24 for B01/B02 or 28
for M2. These are per-operation ceilings, not predicted durations. Fresh source
capture adds its bound at every existing boundary. Journal reads/fsyncs have
finite byte/count bounds but no measured duration or guaranteed aggregate wall
time. Preparation, independent rereading and the two P01 negatives also consume
the same outer guard. No larger guard or adaptive retry is authorized here.

The prestart successor retains a real created-state inspect before start and the
original reader rederives its policy and chronology. The expected keeper is
root (0:0) with init; candidate execution remains the retained explicit
65534:65534 Docker exec. Created-state proof, paused-state continuity, complete
raw captures, request/response order, unchanged staged input, ordinary removal
and authenticated post-removal absence all remain required. Actual physical
qualification and timing measurements are still pending.

## Terminal diagnostics and direct fault witnesses

A qualification failure now retains a terminal failed/unavailable status. The
activity census distinguishes a retained execute intent, a create acknowledgment,
a start acknowledgment, an exec-dispatch intent, individual observed response
phases and complete capture-command records. The last item does not claim the
census reparsed capture content. A dispatch intent alone does not prove that
candidate code ran. A current complete prefix with no dispatch can establish
zero activity; an uncertain prefix gives unknown, while independently
authenticated prior responses can establish a lower bound of one observed
history. Prior-only facts never establish current cleanup or absence. Census
errors cannot heal the journal or turn a failed test into a pass. A killed worker
may leave no completion census; that remains unavailable, never a running result
that can be counted as success.

Each deliberate mutant also requires a compact witness derived from original
response bytes and immutable, read-only SQLite queries under the exact reviewed
schema. D01 must have the exact hashed orphan content absent before and present
after/in the reopen-attempt capture, with injected_failure then invalid_database
responses. This explicitly demonstrates a rejected reopen attempt, not successful
reopening. D02 must return same then MUTATED while the stored receipt remains
same after and on reopen. D03 must list winner, return the corrupted notes in its
final lifecycle_show response, and retain winner in document_state. Witness
records retain original capture/response paths and digests. These are authored
fault-discrimination checks; inherited product assertions and public obligation
coverage are unchanged.

Held-1 sources/evidence are preserved in the isolated package's held-1 directory.
The reporting/witness successor and six new diagnostic controls are held for
scoped verification under the root-owned resource allocation. The independently delivered six
source/layout reports bind the unchanged v1-3 candidate requests.

N01 retains its own terminal status and original-derived activity census even
when revocation fails or unexpectedly dispatches. Class totals include that
separate fresh attempt; an unknown component makes the aggregate unknown. The
primary history count remains separate. N02 reopens the same original and adds
no candidate attempt. Malformed retained dispatch records never establish
absence of dispatch.
