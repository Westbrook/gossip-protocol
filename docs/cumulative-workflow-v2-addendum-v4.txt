Prospective cumulative V2 workflow exposure addendum v4

Status and scope. This addendum applies only to a newly registered cumulative V2 study that explicitly binds its exact bytes together with the immutable library-cumulative-product-v2 contract. It clarifies the prospective product behavior of the existing solution.solve workflow entry point where M4-COMPATIBILITY clause 2 overlaps the mandatory V2 amendments. It does not modify the frozen V0/M1 pilot, oracle, public definitions, immutable seed, previous study contracts, or previous observations. The original eight published workflows retain their inputs and expected outputs. This is public information supplied before candidate generation, not a concealed acceptance bank.

Admission remains separate. Keep the original frozen oracle-admitted input set and its operation-count and JSON input/output size rules: at most 64 operations and 60 KiB each for admitted input and oracle output, using the original admission serialization. The original oracle is an admission guard and historical example source; its modeled answers do not override the applicable V2 product semantics below. No input that the original guard admits may be removed merely because its historical expected answer differs from V2. Inputs rejected by that guard remain outside this workflow product-verdict domain, including malformed shapes or types where the guard rejects them. Their rejection qualifies the evaluator only. Invalid requests at actual product API, CLI, HTTP or browser boundaries remain subject to their own required product tests. Each selected workflow records its original admission decision before candidate execution, without consulting candidate outputs. The historical expected-answer size check remains part of that admission decision; it is not proof that the prospective V2 answer has the same byte length.

Ordinary workflow behavior. Keep the existing input keys, operation names, arguments and published defaults. Operations include import(source,text), list(offset=0,limit=100), search(query,offset=0,limit=100), show(source), export(sources optional), and reopen(); admitted M1 operations include submit(job_id,entries), prepare(job_id), commit(job_id,epoch,fail_before_commit optional boolean, default false), cancel(job_id), retry(job_id), and job(job_id). The optional milestone field retains its original admission behavior and default v0. An otherwise admitted M1 operation in v0/default mode returns unsupported_operation for that operation and processing continues; it is not removed from admission or dispatched as an M1 operation. Output remains results in operation order plus all final six-field documents in source order; milestone=m1 additionally returns all final JOB objects sorted by job_id. Import returns the existing imported/unchanged result and document. Submit/cancel/retry/job return JOB, prepare returns TOKEN, and commit returns RECEIPT with its historical document objects. Omitted export sources selects all documents; an explicit empty sources list selects none. Pagination defaults, source-to-ID conversion, domain-error results, processing after a domain error and the reopened marker remain as specified. Validation failure during prepare persists the required failed JOB while preserving the catalog/content graph. Existing receipt replay, ordering and fresh-value obligations remain binding.

Real execution and isolation. Each solve call creates an isolated temporary input root and database and delegates to the actual application modules. Import writes the supplied UTF-8 bytes under its temporary input root and calls the real file importer; M1-mode job operations invoke the real JobManager/Store; listing/search/export invoke the actual public product interfaces required by the operation, preserving the existing interface obligations. No additional Service layer is required where a direct Store call conforms to those obligations. Reopen closes and reopens the real persisted Store for that call. Separate solve calls must not share their input roots, databases, jobs or documents. An independent in-memory implementation of the oracle, replacement product solver, manufactured call trace or changed immutable solution entry is not conforming.

Prospective V2 results. The workflow exposes the actual product operations under every applicable V2 rule; it is not an exception from counter validation, counter exhaustion, durable control/fencing, portable M1 hash serialization, receipt preservation or other applicable amendments. This does not add new workflow operation names or imply that workflow tests cover interfaces and behaviors they do not execute. For an admitted commit operation in milestone=m1 mode, epoch must be an exact integer in 1..9223372036854775807. The actual JobManager validates this domain before lookup or database access, so an admitted out-of-range or wrongly typed token yields {"error":"invalid_request"}, including when the named job does not exist. Do not round, clamp, coerce, substitute a token, fabricate a matching job or translate this result back to the old oracle's stale_epoch/not_found answer. Valid-domain tokens retain the applicable identity/token/state precedence and receipt semantics. Required counter increments beyond the maximum fail atomically with counter_exhausted and the preservation required by V2; no-increment operations remain usable at the maximum.

Admitted versus malformed examples. In milestone=m1 mode, the original oracle admits a positive integer epoch of 9223372036854775808. Its historical model yields stale_epoch for an existing different-epoch job, or not_found for an absent job; this prospective workflow instead returns invalid_request from the actual V2 JobManager in both cases and continues subsequent admitted operations. The original guard's epoch/type validation depends on the preceding modeled job lookup: a wrongly typed or nonpositive epoch can be rejected for an existing job yet admitted when that job is absent. Preserve that admission distinction rather than silently making the input domain narrower or broader. Where the original guard admits the absent-job case, the V2 result is invalid_request; where it rejects a workflow, no candidate correctness verdict is assigned through this oracle. Supplementary cases must retain both the original admission decision and the prospectively authored V2 expectation explicitly. This epoch clarification does not invent validation rules for other workflow-only fields whose checks the historical oracle bypasses after an absent-job lookup. In particular, it does not turn every malformed fail_before_commit value into invalid_request: with a valid-domain epoch, preserve the applicable missing-job result; with an invalid epoch, the V2 token error precedes lookup. Ordinary admitted boolean fault-hook behavior remains unchanged: fail_before_commit defaults to false; the true evaluator-only hook triggers after provisional writes and before commit, returning injected_failure with document/blob/job/receipt changes rolled back, the job still running, and the prior catalog usable. The hook remains prohibited as an HTTP/browser request field. A matching end-state alone does not qualify hook placement.

Prospective evaluator result-size support. Preserve the original 61440-byte input limit and original 61440-byte modeled-answer admission check. Independently authored V2 expected answers use the original oracle's result JSON serialization for size accounting. The new evaluator must support normalized V2 answers through 61824 bytes: the additional 384 bytes allow at most 64 operation results, each changing not_found to invalid_request by six bytes, or stale_epoch to invalid_request by four. These token rejections neither mutate isolated workflow state nor add result items; other prescribed result shapes and ordering remain unchanged. This is an explicit prospective evaluator support-limit change requiring its own source/limits binding and qualification, not a new mandated raw JSON serialization or product error rule. The evaluator must not fail a correct admitted V2 answer for this required error-string growth, nor truncate, omit or reclassify admitted inputs to fit the old ceiling.

The frozen historical-answer admission size, the independently authored normalized V2 expected-answer size, and the bounded raw candidate capture are separate quantities. The physical profile declares enough raw capture capacity for its fixed evaluator framing and serialization; candidate whitespace or alternative equivalent JSON spelling does not by itself establish a semantic product failure. If capture is incomplete, oversized or truncated before a reliable complete semantic comparison, preserve infrastructure/unavailable evidence rather than inventing a wrong product value. An independently derived correct normalized answer above the proposed support ceiling leaves the profile unqualified until an explicit public decision resolves that discrepancy; it cannot quietly remove the admitted input. Neither running the original guard nor preparing expected answers proves candidate behavior. Historical admission, receipts and funding authorizations remain unchanged.
