# C01/C02 finite CLI qualification v4

This is a prospective harness qualification plan, not product acceptance or a
comparison between orchestration policies. The root verification owner freezes
its exact source, provider definitions, observer, controller, transport, runtime,
limits and ordered roster before any physical run. The unchanged corrected-v2
reference contributes candidate source bytes only; it never supplies expected
answers. No generated candidate module is imported on the host.

## Declared scope

The finite roster contains 57 histories in 19 families. Every selected command
runs as the main process of a fresh container. Commands within one history share
that history's isolated, bounded database volume and read-only input fixture.
Different histories have distinct volumes, source staging, input roots and
container identities. A history is an ordered sequence, not a single favorable
command result. The roster census retains each case as observed, partial,
product-failed, observation-unavailable, infrastructure-failed or not-run, with
its exact supported/unspecified assertion sets. No empty assertion dictionary
can qualify by vacuous truth.

The controller uses the explicitly versioned C01 local Unix Docker Engine
API 1.47 profile: non-TTY attach before start, independent wait plus exact-ID
inspect, no init intermediary and no automatic removal. The shared database
volume is a 32 MiB tmpfs volume. The default 4 MiB stream observation cap and
command deadline are evaluator limits, not extra product requirements. A cap,
transport fault, incomplete stream framing, forced termination or missing
completion evidence cannot become a passing product observation.

Each completed process retains its raw stdout and stderr, actual argv, container
identity, wait/inspect evidence, source/fixture/runtime identities and cleanup
records. Candidate text resembling completion evidence has no authority over
process completion. Expected values and evaluation policy stay host-side.

## Normative limits

Only the provider's source-supported predicates are scored. Successful data
commands must emit one semantic JSON value on stdout and exit zero. Applicable
domain failures must emit the specified error message on stderr and exit two.
Argparse usage failures must exit two; they need not emit domain-error JSON.
Legal JSON whitespace/key order and unrelated diagnostics on the opposite
stream are allowed by this qualification. Both streams remain retained.

The exact CLI import and jobs outer wrappers remain inferential under the blind
normative review. These facets stay explicitly unqualified; they do not become
mandatory failures or pass credit merely because the reference uses a natural
shape. Mixed diagnostic/error framing likewise cannot pass by searching for an
expected substring or fail solely because an unstated pure-stderr rule was
invented. Independently proved wrong exit, channel, message shape, fixed error
code or semantic value remains a failure.

## Physical controls

The qualification separately exercises the evidence pipeline with bounded
synthetic candidate sources. These are declared controls, not additional
product histories or statistical samples:

- Semantic success JSON and exit zero with legal whitespace/key ordering and
  diagnostic stderr; a domain error on stderr and exit two with diagnostic
  stdout; usage prose and exit two.
- Exact arbitrary bytes on both output streams, including NUL, non-UTF-8 bytes
  and bytes resembling Docker multiplex headers, to establish raw demultiplexing.
- Correct-looking output and forged completion text followed by a bounded hang,
  which must remain observation-unavailable despite any apparent answer.
- Output beyond a prospectively declared capture cap, which must preserve the
  observation-limit reason and must not become a product failure.
- A genuinely missing executable, kept distinct from a successfully started
  process that naturally exits nonzero.
- Wrong exit, wrong prescribed channel and wrong semantic value, each with
  otherwise completed transport, to show that the corresponding supported
  predicate distinguishes the defect.
- Independent invocations sharing one history database, followed by a separate
  history root with no inherited state. Retained container IDs establish actual
  separate processes; semantic readback establishes persistence/isolation.

A costly physical OOM run is not required here. Deterministic offline evidence
must still distinguish OOM, startup failure, ordinary nonzero exit and capture
failure. A synthetic source control never closes a reference-product obligation.

per-history outcomes, and a terminal census containing all planned identities.

Supported success and partial observations are reported separately. A method

## Retained mount identity boundary

The retained mount rule follows the tracked `candidate-b03-mount-inventory-plan-v1`
design. Only the top-level inspection `Mounts` collection receives
inventory-based comparison: each exact, unique canonical absolute Destination
maps to its complete unchanged row. Every field, including unknown fields and
nested arrays, remains present and type-sensitive. Raw ordered views and their
original destination sequences remain retained. This does not declare
`HostConfig.Mounts`, argv, environment or any other array unordered.

The physical qualification reconstructs inventories independently from strict
raw CLI and Engine HTTP JSON, rejecting duplicate object keys before conversion.
It verifies full-view hashes separately from immutable-projection hashes,
ordered destination sequences, full per-destination row hashes, canonical
inventory hashes, comparison-view hashes, policy/runtime/role/phase binding and
the complete comparison-record digest. Non-Mounts identity must remain exact,
except for the independently authorized typed false-to-null OOM-default
transition in the two startup phases. It is forbidden during prestart or later
running-holder comparisons. Raw evidence is never rewritten by normalization.

Candidate prestart comparison has its own durable
`step-NNN-prestart-comparison.json`; checkpoint ordering must place it before
attach and start requests. Final comparison retains the distinct
`step-NNN-startup-comparison.json`. Their identities are never merged into one
startup marker. Holder startup and subsequent boundaries retain their separate
comparison evidence, continuous process identity and unchanged bounded volume.
Product observations and the full false/unknown/unspecified census are saved
before these qualification assertions, including failures and not-run cases.

The v4 execution, transport and observer domains are new. The shared v1 provider,
57 histories, 305 commands, 900 assertion cells, 32 unspecified cells, and all
eleven control sources, literal argv, expected results and limits are unchanged
from frozen v3 at `f2bdbf1`. The corrected-v2
reference bytes are unchanged. Every earlier version and failed receipt keeps
its original disposition; no result is retroactively promoted.

Stage one contains exactly the designated one-history, nine-command persistence
qualification and all eleven controls. Only a terminal stage-one pass permits

## Version-four startup rejection qualification

This version implements the separately reviewed
`analysis/candidate-b03-empty-command-plan-v3.json`. The registered missing
executable and its zero-argument invocation are unchanged. Explicit `Cmd:null`
is supported only by the pinned runtime and exact independently declared argv;
raw null and an empty list remain different identities across snapshots.

All raw container and volume inspection bodies are bounded and strictly decoded
before use, including the four raw-control sites omitted by the frozen v3 helper.
Duplicate object keys, invalid UTF-8, nonfinite numbers and excessive structure
are rejected. Frozen v3 remains failed and unmodified.

The generic transport now retains a distinct start-response-completion receipt
after complete HTTP framing, observed socket EOF and successful durable response
retention. It precedes rejection cleanup. The final transport result follows
cleanup and binds the same completion object and receipt descriptor. Missing or
failed retention leaves both fields unavailable. A `start_error` label or response
filename alone cannot qualify the control.

The qualification independently authenticates request/response bytes, descriptors
and external checkpoint chronology. Its finite HTTP parser rejects ambiguous
framing, duplicate or control-bearing headers, incomplete bodies/chunks, trailers,
extra responses and exceeded limits. File EOF is never proof of socket EOF.
Only a complete HTTP400 ErrorResponse with its single nonempty `message` field,
the pinned Engine invalid-command classifier, exact matching cleanup State.Error
and the declared absent executable qualifies this particular control. HTTP500
and unrelated errors remain unqualified without retries.

Each authenticated cleanup view must show an unchanged zero StartedAt, created
status, exact false running/paused/restarting/dead/OOM flags, integer zero PID and
restart count, and integer127 daemon rejection bookkeeping. That127 is never a
candidate exit. There is no wait, final startup comparison, natural completion
or product acceptance. Defensive kill requests and incomplete attach EOF do not
assert that a process ran. Owned container and volume removal and exact-name
absence are independently checked.

A separate qualification-owned `candidate-created-to-start-rejected` identity
phase reconstructs the complete immutable views and destination inventories only
after authenticating this rejection proof. It retains all raw fields, hashes,
orders and transformations, and permits only the pinned typed false-to-null
OOM-default change alongside the existing top-level Mounts inventory rule. Later
CLI continuity keeps OOM exact. No generic production identity phase or observer
predicate receives this authority.

Offline `CandidateClientRejectionProofV4Tests` covers raw framing/JSON boundaries,
complete versus absent or forged response evidence, state/identity substitutions
and diagnostic comparison limits. The five physical classes and eleven control
definitions retain their existing census. Root owns the combined verification,
source freeze and controls-plus-persistence barrier before any bulk history.
