# Cumulative M4 reference application

M4 adds the migration and release milestone to the authored Local Research
Library benchmark: a normalized revision catalog, compatible versioned clients,
independently constructed legacy snapshots, and an installable deterministic
release. This is development qualification of a trusted reference application.
It is not a model-generated result or evidence that a swarm outperforms a central
orchestrator. The four-milestone, six-trajectory comparison remains open.

The normative prospective contract is `library-cumulative-product-v1.json`,
SHA-256 `3353dbaa0c2474527cbffb0d87a4091b5f77ed3f98418fff2f216d90b6a8487c`.
The reference does not silently amend it. The machine-readable qualification
checkpoint is `analysis/library-m4-reference-checkpoint-v1.json`.

## Qualified development result

The final combined run physically passed **74/74 checks in 14 classes**, with
no skips, reused classes or stale input/runtime bindings. All 382 retained input
hashes matched current source. The 18 current M4 host verdicts passed alongside
8 M1, 12 M2 and 10 M3 inherited histories, deterministic release/public workflows,
and six desktop/mobile browser contexts. A deliberate revision-identity defect
was rejected. Raw exact-comparison receipts remain distinct from the versioned
host oracle; the checkpoint links both and preserves all four earlier failed
qualification attempts. No provider calls or API spend occurred.

## Application and release

`gossip_harness.library_m4_reference_v1.m4_files()` composes the complete text
application from additive overlays over frozen M1–M3 generators.
`m4_binary_files()` supplies exact independently frozen SQLite bytes separately;
`write_m4_project(path)` stages both into a fresh destination without replacement.
The database uses `document_state` and `document_revisions`, with no legacy
lifecycle/revision shadow tables or views. Revision identity binds document ID,
revision number and blob ID, including restore followed by different content at
the same revision number. Legacy numbered response shapes remain available.

The maintained browser uses the versioned lifecycle API and displays revision
IDs. Portable export still defaults to v2; v4 is an explicit format selection.
A document removed by another client's restore cannot silently discard an
unsaved local draft. Explicit Reload remains the discard action.

From an authored application, `python -m library.clients.release --output DIR`
creates a fresh package with an explicit file allowlist and canonical manifest.
It includes the immutable seeds, full application, four operator guides, public
migration snapshots, public regression driver and a versioned seven-operation
dataset workflow. It excludes local databases, credentials and private
acceptance definitions. The manifest binds every file's bytes and hash, the
product contract, API/storage version and pinned Python 3.12 image. It contains
no timestamps or machine-specific source paths.

Publication uses exclusive rename on supported Linux/macOS systems. Existing
output directories remain untouched, including a competing publisher's empty
directory. Directory traversal checks each lexical component without following
symlinks before processing `..`; this matters because real Python imports can
retain `link/../source` in a module's `__file__`.

## Independent evidence and verification boundaries

Public v0/M2 databases were constructed with independent SQL and frozen before
root reference evaluation. Their inventories include Unicode, empty/shared
content, revision ABA, tombstones, annotations, collections and serialized job
receipts across reachable states. The public regression driver copies those
bytes into isolated mutable databases and exercises the actual application.
It also runs the declared dataset workflow twice across reopen boundaries.

A separate author froze 18 M4 histories without inspecting M4 implementation or
implementation tests. These exercise migration, exact legacy serialization,
versioned APIs/CLI, canonical export, revision identity and nine corruption
refusals. Inputs and host-side expectations remain distinct from the child
observer. They are development tests, not concealed held-out statistical data.
The pre-reference receipts retain both the public assets and the independent
case definitions; changing a definition requires an explicit new version.

The first execution exposed two v1 evaluator defects: it privately required
worker generation to stay exactly zero after restore, and attempted to serialize
the legacy byte-encoded Service export as a JSON object. Version 2 preserves the
original frozen definitions and failures, strictly decodes only that documented
legacy export, and checks the permitted post-restore worker-generation domain
on the host. It does not replace zero with the observed value one. All other
fields remain exact comparisons. The raw execution receipt remains unchanged;
a separately bound host-verdict receipt identifies the versioned oracle. Error,
timeout and infrastructure outcomes cannot become correctness passes. Version 3
adds the same strict JSON decoding for the byte body of the explicitly named
POST `/api/v1/export` transport adapter; v2 inputs, expected values and host scorer
remain unchanged. The v2 error is also retained.

Combined qualification runs the central static gate and selected offline
classes before fresh pinned Docker and browser lanes. Docker runs the inherited
8 M1, 12 M2 and 10 M3 histories unchanged, then the 18 M4 histories. A deliberate
revision-identity defect must be rejected as `wrong_answer`. A separate actual
release is built twice in the pinned image; its installed public regressions
run against the delivered files.

Browser qualification serves freshly built packages, not source staging. Three
fixtures each use isolated desktop/mobile contexts for cumulative lifecycle,
recovery/export and the dataset handoff. Retained evidence includes raw HTTP
bodies, downloads, CLI reopen observations, release manifests, source hashes,
traces and screenshots. Actual outcomes and any failures/skips are recorded in
the checkpoint; these descriptions alone are not execution claims.

Authored migration tests use real process exits before/after commit and a hot
SQLite rollback journal. Ordinary corrupt/unknown inputs are refused without
rewriting their database bytes. A genuine hot journal is recovered under
exclusive authority before committed-state validation; this is recovery, not
permission to repair arbitrary corrupt input. These declared reference hooks
are not arbitrary-candidate crash acceptance or physical power-loss proof.

## Explicit policies and unresolved contract decisions

Schema3→4 migration rotates the incarnation to fence supported old M3 handles
before they can write using removed tables. Other existing controls, high-water
marks, job serialization and generation are preserved. This is a necessary
interpretation of the contract's broad control-preservation language and must
be made explicit before freezing a cross-implementation candidate contract.

Opening a copied database does not rebind its durable backup ownership or erase
its registry. The default directory remains beside the copied database in
memory; backup I/O fails closed if that differs from recorded ownership until
an explicit directory configuration is supplied. Portable schema3 inputs need
not contain the reference-specific `backup_root` key: an unbound marker retains
relative ownership records, and explicit directory adoption preserves them.
The migration CLI dispatches before Service configuration. Multi-root registry
semantics still need a public contract decision.

Portable schema4 inputs need not use the reference's triggers. After validating
such an input, the reference installs its own high-water fences under exclusive
authority. Normal already-authored schema4 opens remain read-only. Replacing
these implementation mechanisms is not evidence of a logical migration.

The reference preserves an incoming `last_error` control during migration.
The inherited diagnostics rule says success clears an error for that operation;
a pre-existing migrate error therefore exposes an unresolved specification
precedence question. Do not claim that corner is fully contract-qualified.

The earlier signed-64-bit counter/exhaustion ambiguity, frozen M1 content-hash
serialization detail, worker idle/stopped distinction and generic candidate
crash-acceptance gaps remain open. Passing finite reference checks does not
close them or establish whole-project study acceptance.
