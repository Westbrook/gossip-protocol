# Actual worker exits and protected Git completion evidence

The cumulative study now has a host-owned producer for role-process and final
source records. It launches the registered workers, retains their original
events, reaps the actual process handles, and connects those observations to
the V4 financial completion request. A worker's final message alone cannot
close the cohort.

This is infrastructure for the larger comparison. It adds **zero comparative
model-quality observations** and does not demonstrate a gossip or swarm benefit.
The complete controller, independent product acceptance, matching rehearsal,
and larger live comparison still require integration and qualification.

## Process and source contract

`ProcessEvidence` receives the prospective six-child roster, this child's
identity, the caller-owned checkpoint and independently expected head, and the
actual protected `GitStore`. Registration binds the repository pathname,
directory identity and harness marker before workers launch. The accepted Git
commit may advance during normal project work; the repository cannot be
substituted at closure.

Each launch has a fresh nonce, registered actor and generation, explicit
argument/environment digests, a distinct evidence directory and a new process
session. The producer retains the `Popen` handle before publishing the launch
record, so an uncertain publication cannot lose the handle needed for cleanup.
It never retries a generation automatically. A second generation requires an
authenticated stop for the first; the current contract permits at most two.

The trusted role helper writes exclusive, canonical ready/final records. The
parent checks their exact typed identity and actual owned PID. It calls
`Popen.wait` and verifies that the owned process group is absent. The final
record may precede actual cleanup, so it cannot substitute for this wait.
Missing or changed events remain errors in the original wait record.

Completed closure requires every registered role's latest incarnation to have
valid original ready/final events, a zero exit, a stopped outcome, no declared
remaining actions and no event errors. Earlier restart generations remain in
the record. Failed cohorts can record never-launched roles and known launch
failures, explicitly without claiming they all ran. An unclassified launch
exception or unproved process stop cannot be silently turned into closure.

After admission closes permanently, the producer reads the actual protected
commit, Git tree and complete bounded blob inventory. Its source digest uses
the existing observation-admission protocol shared with the candidate observers.
It emits financial-compatible role-stop and terminal records, then a prepared
closure. The original checkpoint and Git identity are checked again before an
acknowledged confirmation binds that exact closure, source and request.

`verified_request(expected_head)` is an owner-only handoff after a successful
finalization. It checks the original confirmation and current protected source
before the separate financial transaction. Prepared closure files without a
confirmation are not proof that finalization succeeded. The full rehearsal
reader must enforce this distinction; the generic financial V4 assertion parser
does not enforce the process producer's additional contract by itself.

## Chronology and failure handling

`CheckpointChain.position(name)` authenticates the requested raw bytes and
their exact committed delta, then returns the acknowledged one-based append
position. Owner and external-head checks surround the observation. The method
preserves existing append and wire behavior and rejects unknown or unacknowledged
records, tampering and lost ownership. It is a point lookup, not a substitute
for full-boundary validation.

Exit observations and stopped-failure records can use the checkpoint's existing
cleanup reserve; normal launch records cannot. This makes that reserve usable
when normal admission capacity is exhausted. It does not create a separate
guaranteed reservation per child. If cleanup capacity itself is exhausted or
the chain is uncertain, the controller must preserve evidence and explicitly
clean up the owned handles without pretending it obtained a terminal proof.

## Evidence boundaries

- These are trusted-host observations, not cryptographic remote attestation.
- Group absence covers the owned process group. It does not discover a
  descendant that deliberately escapes into a new session.
- Append positions order the parent's retained observations. They do not prove
  child write times or that readiness was observed while the child was alive.
  A live readiness barrier remains the controller's responsibility.
- Completed/remaining action IDs are role declarations. The complete controller
  and qualification reader must reconcile them with the registered work and
  original action/result records.
- Git, checkpoint and SQLite operations are separate. There is no cross-store
  atomic commit, continuous filesystem attestation or guarantee of future Git
  stability. Consumers must check the exact evidence they use.
- The producer does not adopt process handles after a controller crash. The
  planned builder restart is a distinct, explicitly owned operation.
- No candidate correctness, complete acceptance, provider permission or new
  spending authorization is supplied by this component.

## Verification and remaining integration

The registered verification batch covers 29 process/Git/financial composition
methods, 13 new point-position methods, and 227 affected inherited checkpoint
and financial methods. The machine-readable checkpoint records the exact final
outcome, source/runtime identities, class rosters and retained review receipt:
[process evidence integration](../analysis/cumulative-process-evidence-integration-v1.json).

The actual process controls include an eight-role completion joined to a
disposable financial seal, deliberate exit-86 restart, a live descendant after
leader exit, missing/changed events, launch/publication uncertainty, protected
repository substitution, a postpublication Git change, confirmation tampering,
and cleanup after normal capacity exhaustion. Other negative controls explicitly
inject boundary failures. None uses a real provider or a candidate container.

Independent source review corrected stale readiness acceptance, a boolean
generation alias, late repository selection, the publication-window Git check,
unused cleanup capacity and ambiguity between a prepared and confirmed closure.
Earlier focused logs remain retained rather than being relabeled as final
combined qualification.

The next integration must connect this producer to all six ordered trajectories
and four milestones, require confirmed original completion in the rehearsal
reader, complete semantic acceptance and the remaining product observations,
then qualify the combined physical contract and one complete matching
zero-provider rehearsal. Independent held-out confirmation and the separate
placement-versus-transport comparison remain required experimental work.
