# C01/C02 finite CLI qualification v2

This is a prospective harness qualification plan, not product acceptance or a
comparison between orchestration policies. The root verification owner freezes
its exact source, provider definitions, observer, controller, transport, runtime,
limits and ordered roster before any physical run. The unchanged corrected-v2
reference contributes candidate source bytes only; it never supplies expected
answers. No generated candidate module is imported on the host.

## Declared scope

The finite roster contains 57 histories in 19 families. Every selected command
runs as the main process of a fresh container. Commands within one history share
that history's isolated, bounded database volume and read-only input fixture.
Different histories have distinct volumes, source staging, input roots and
container identities. A history is an ordered sequence, not a single favorable
command result. The roster census retains each case as observed, partial,
product-failed, observation-unavailable, infrastructure-failed or not-run, with
its exact supported/unspecified assertion sets. No empty assertion dictionary
can qualify by vacuous truth.

The controller uses the explicitly versioned C01 local Unix Docker Engine
API 1.47 profile: non-TTY attach before start, independent wait plus exact-ID
inspect, no init intermediary and no automatic removal. The shared database
volume is a 32 MiB tmpfs volume. The default 4 MiB stream observation cap and
command deadline are evaluator limits, not extra product requirements. A cap,
transport fault, incomplete stream framing, forced termination or missing
completion evidence cannot become a passing product observation.

Each completed process retains its raw stdout and stderr, actual argv, container
identity, wait/inspect evidence, source/fixture/runtime identities and cleanup
records. Candidate text resembling completion evidence has no authority over
process completion. Expected values and evaluation policy stay host-side.

## Normative limits

Only the provider's source-supported predicates are scored. Successful data
commands must emit one semantic JSON value on stdout and exit zero. Applicable
domain failures must emit the specified error message on stderr and exit two.
Argparse usage failures must exit two; they need not emit domain-error JSON.
Legal JSON whitespace/key order and unrelated diagnostics on the opposite
stream are allowed by this qualification. Both streams remain retained.

The exact CLI import and jobs outer wrappers remain inferential under the blind
normative review. These facets stay explicitly unqualified; they do not become
mandatory failures or pass credit merely because the reference uses a natural
shape. Mixed diagnostic/error framing likewise cannot pass by searching for an
expected substring or fail solely because an unstated pure-stderr rule was
invented. Independently proved wrong exit, channel, message shape, fixed error
code or semantic value remains a failure.

## Physical controls

The qualification separately exercises the evidence pipeline with bounded
synthetic candidate sources. These are declared controls, not additional
product histories or statistical samples:

- Semantic success JSON and exit zero with legal whitespace/key ordering and
  diagnostic stderr; a domain error on stderr and exit two with diagnostic
  stdout; usage prose and exit two.
- Exact arbitrary bytes on both output streams, including NUL, non-UTF-8 bytes
  and bytes resembling Docker multiplex headers, to establish raw demultiplexing.
- Correct-looking output and forged completion text followed by a bounded hang,
  which must remain observation-unavailable despite any apparent answer.
- Output beyond a prospectively declared capture cap, which must preserve the
  observation-limit reason and must not become a product failure.
- A genuinely missing executable, kept distinct from a successfully started
  process that naturally exits nonzero.
- Wrong exit, wrong prescribed channel and wrong semantic value, each with
  otherwise completed transport, to show that the corresponding supported
  predicate distinguishes the defect.
- Independent invocations sharing one history database, followed by a separate
  history root with no inherited state. Retained container IDs establish actual
  separate processes; semantic readback establishes persistence/isolation.

A costly physical OOM run is not required here. Deterministic offline evidence
must still distinguish OOM, startup failure, ordinary nonzero exit and capture
failure. A synthetic source control never closes a reference-product obligation.

## Evidence and remaining work

Each matrix writes a prospective ordered roster before dispatch, durable
per-history outcomes, and a terminal census containing all planned identities.
Failed, unavailable and interrupted histories stay visible, including every
not-run case. Every qualified observation must match the exact provider-declared
assertion-key census; any missing or unexpected key fails qualification.
Supported success and partial observations are reported separately. A method
pass is evidence about this finite qualification, not a claim that all 57
histories passed every product obligation.

The root owner runs the combined static gate and relevant fast methods before
the changed-contract Docker lane, then reconciles exact source fingerprints and
performs an independent retained-evidence audit. No contributor runs Docker or
rehearses candidate behavior before that freeze. No provider API calls or paid
experiments are part of this qualification.

This slice does not close all four CLI requirement IDs or B03. Loopback listener,
HTTP wire boundaries, actual browser actions/export, later process recovery and
release obligations, production ScopePlan/prerequisite authority, the complete
four-milestone/six-trajectory study and fresh independent acceptance remain
separate work. Qualification records have purpose `harness_qualification`, no
Registry admission and no production authority or acceptance credit.

The four reference classes partition every provider family exactly once. The
reference totals are 57 histories and 305 invocations. There are eleven separate
synthetic/raw control histories, each with one candidate container attempt. Ten
synthetic controls execute the closed one-step `cli-grammar-missing-command`
recipe using their own fixed Git source. Their registered provider-case verdict
is retained separately from the authored transport-control verdict. For example,
a synthetic exit-zero transport positive still fails the registered usage
case's exit-two predicate; its transport-control success does not rewrite that
product-case observation. The missing-executable control uses the raw transport
API with its own disclosed argv, and receives no provider-case verdict.

The revised C01 profile adds one trusted volume holder to each controller
history. It mounts only that history's `/tmp` volume, read-only, with no candidate
source or input mounts. A fixed, bounded sleep under the pinned image holds the
32 MiB tmpfs mount across finite-process exits. Its exact identity, startup time,
restart count, configuration and running state are retained before and after
every command. Cleanup removes owned finite containers, then the holder, then
the volume. The raw startup control needs no persistence holder.

Consequently the complete prospective qualification is 68 history volumes,
316 candidate container attempts and 67 trusted holder containers: 383 created
containers if all creates succeed. The missing executable must not count as a
successfully started candidate process. Started candidates, natural completions,
controller kill requests, independently proved forced termination, startup
unavailability and holder lifecycles are separate counts. An output-limited
process may or may not have a separately proven natural exit; the retained
observation decides that count. The deliberately hung control cannot qualify
from its forged completion text.

## Version-two compatibility boundary

Version two changes the execution/transport/observer identity domains and the
startup identity comparison policy. It preserves the shared v1 case provider,
all 57 histories, 305 commands, 900 assertion cells and 32 explicitly
unspecified cells. The eleven control sources, literal candidate argv, expected
values, stream policies and deadlines are byte/data equivalent to the frozen
v1 test definitions at commit `3ff8d94238f673a0af0660e7ddff196dceec4130`.
The corrected-v2 reference source bytes are unchanged. Earlier v1 failures and
receipts retain their original identity and disposition.

A narrowly declared, runtime-bound policy accounts for the startup transition
of `HostConfig.OomKillDisable` from the JSON boolean `false` to JSON `null` only
on the supported Engine profile and phases. The raw inspections remain intact.
Qualification checks the policy ID, full definition/digest, runtime digest,
raw projection hashes, transformed comparison hashes, exact transformation
record and comparison self-digest, then independently recomputes the comparison
from the retained inspections. Candidate comparisons use the complete immutable
projection. The holder's created-to-running comparison excludes only its
expected `StartedAt` transition; every subsequent holder boundary comparison is
byte-exact canonical JSON, preserving type distinctions such as boolean versus
integer. This policy does not authorize changes to memory limits, mounts,
identity, argv, privileges, networking, OOM evidence or lifecycle checks.

Controller and transport intent records have distinct names:
`step-NNN-controller-intent.json` precedes container creation and
`step-NNN-intent.json` precedes transport start. Both remain independently
retained with external checkpoints. This prospective separation fixes an
exclusive-journal filename collision without modifying frozen v1 artifacts.

Root qualifies v2 controls and the designated nine-invocation persistence
history before the remaining 296 reference invocations. Matching receipts may
be reused only for this exact v2 qualification purpose and frozen identities.
A v2 observation never receives a v1 execution identity, and new compatibility
handling never converts a historical failure into a pass. Counts and required
remaining project work above are unchanged.
