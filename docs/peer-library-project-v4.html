A live twenty-role M1 development pilot

Status: current source passed 361 offline qualification checks. A complete v4 twenty-role physical rehearsal and live pilot remain pending; no v4 live allocation or provider call is recorded. This pilot asks whether sixteen independently prompted builders and four stronger reviewers can produce, integrate and repair a useful software milestone. It is a bounded development observation before the larger comparative study, not an estimate of swarm superiority.

The project is the Local Research Library: a working Python/SQLite application with a CLI, HTTP API and browser client. M1 adds bounded directory, ZIP and JSON ingestion, persistent job progress, cancellation/retry fencing, atomic commits and per-source document identity while preserving inherited import, search and export behavior. Identical content may share a blob without collapsing distinct documents. The immutable seed README together with the prospective public M1-UI-AUTOMATION-V4 addendum supplies the product and interface contract; the public histories are examples, not the entire specification.

The primary question is accepted behavior with retained progress: does the integrated application meet the whole M1 obligation, and does public failure evidence lead to a sound correction before the fixed limits expire? A smaller token bill or faster response cannot compensate for data loss, a broken inherited workflow, an invalid release or an unfinished obligation.

Each role has isolated local evidence, action history and Git state. Transport continues while model work is outstanding. The initial builder requests contain the public task and seed, with no sibling implementation. All four candidates for a package address the same work package; this is four-way implementation diversity, not sixteen independent features. Twenty roles also do not imply twenty simultaneous provider requests.

The controller schedules fixed phases and routes bounded repairs from public outcomes. Models author the implementations, choose candidates and return review decisions; gossip distributes the evidence those decisions consume. This pilot does not have peer-local task planning, a matched orchestrator control, a partition schedule or process-restart intervention. It cannot identify whether gossip, role count, model mix or the controller caused an observed outcome.

Builders and reviewers use structured responses and have no execution tool in this pilot. The harness executes the public suite on the actual merged source. Reviewers can identify defects and suggest probes in their rationale, but this version does not implement the larger study's adaptive selection and execution of model-proposed distinguishing tests. Neither model confidence nor agreement between candidates substitutes for an executed check.

The bounded project loop

  1. Sixteen blind builders propose complete file changes within their exact package scopes. The harness retains valid and invalid outcomes and verifies eligible Git contributions against the accounted model request and result.
  2. A complete eligible frontier is sealed. R1 nominates one candidate per package. The selected topics are structurally merged without advancing the protected accepted branch.
  3. The exact combined tree executes the frozen public histories in the pinned Docker sandbox. Four reviewers receive the target, source, selection and public execution receipts through their local evidence views. Required checks and all eight current scoped approvals gate release.
  4. Public failure or a valid review rejection can trigger repairs to implicated selected topics. A subsequent combined tree requires a new physical public evaluation and fresh reviews. At most two source-repair rounds follow the initial proposals.
  5. Public release, a fixed resource limit, an unrecoverable provider outcome or an infrastructure/accounting failure ends new dispatch. The complete cohort is reconciled and frozen before independent interface and browser acceptance. Acceptance outcomes never become model repair feedback.

Source identity, actual materialized evidence, instructions, model profile and scope are bound to each dispatch. A listed event ID without its locally arrived payload is insufficient. Later results cannot be appended to an already sealed frontier, and stale approvals cannot approve a newer target. An invalid candidate can reduce the initial choice set; a package with no eligible candidate is a terminal observation rather than permission to invent or silently replace one.

The aggregate allowance is 54 admitted model actions:

Review 24 Twelve original reviews plus at most one format correction for each

Each builder has a ceiling of three calls. R1 has twelve because it also selects; R2–R4 have six each. Those role ceilings and the 78 prospectively registered possible action identities do not grant 78 calls: the stricter aggregate, action-kind and generation limits apply across the whole cohort. Failed and unknown admitted calls still consume their allowances. Exact replay of the same accounted request must not invoke the provider or consume a new slot.

A known-complete malformed selector or reviewer response may receive one schema correction. The correction preserves the original semantic instructions, source and complete evidence; only its registered work identity and closed diagnostic metadata change. It is a new paid action. A well-formed rejection remains a rejection and may lead to source repair, not a disguised format retry. Builders have no separate format-correction allowance. Ambiguous provider completion retains its reservation and is not automatically reinvoked.

Distributed Git repairs and semantic conflicts

The initial alternatives live in private Git stores and move as authenticated commits and bundles. This supports the useful part of a distributed Git workflow: independent topic development, retained ancestry, inspectable alternatives and an explicit integration decision. Git resolves byte-level histories; it does not resolve disagreement over document identity, transaction boundaries or the cancellation protocol. A clean merge therefore remains only a candidate tree.

The v4 repair design separates the patch base from the integration context. Each repairing builder starts from its exact selected package topic commit. It also receives the full failed combined source and authenticated public execution and review evidence as read-only context. Its new commit may change only the registered package files. It cannot acquire another package's introduced history by branching from the failed combined tree.

The next frontier contains exactly those repaired topics and the unchanged previously selected topics. They are restaged together from the accepted baseline and receive combined evaluation and review again. Package generations advance independently: catalog's second repair and query's first repair may belong to the same global round. Initial alternatives and failed combined trees remain retained even though repair rounds do not reopen the entire sixteen-candidate competition.

This addresses simultaneous repairs without weakening Git scope checks, including checks on foreign changes later reverted in a branch's history. The plan, target, selection and feedback must still be current at admission and frontier sealing. Historical immutable evidence remains verifiable after a successor exists. Final promotion remains an authoritative compare-and-swap on the protected accepted head; distributed proposal ownership does not eliminate that integration boundary.

Capacity, money and bounded stopping

Full normalized requests, financial envelopes and actual encoded HTTP requests each face their declared 512,000-byte bound. Escaping and wrappers count; a source-size estimate alone is insufficient. The controller must not shorten a candidate or drop alternatives to make selection fit. Capacity exhaustion is a retained resource outcome, not a finding that the application is incorrect.

Independent M1 acceptance after freeze

Public promotion is separate from final acceptance. Before private observations, the trusted controller must bind the exact cohort/member, commit, tree, files and execution contract to a terminal freeze, reconcile financial activity and prohibit further model dispatch. A partial or rejected project is retained at that same boundary. A quiescent individual role is not the whole-cohort barrier.

The new interface adapter defines five independent host-judged scenarios:

  • Directory, ZIP and JSON intake with persistent content and per-source identity.
  • Traversal, symlink, invalid UTF-8 and oversized-input rejection without partial document or job creation.
  • Cancellation, retry, stale-result fencing and rollback through real storage and job modules.
  • Actual CLI invocations, durable state across invocations and idempotent replay.
  • A real loopback HTTP server, restart persistence shared with CLI/storage and malformed request handling.

Candidate Python executes inside the existing pinned Docker sandbox. The trusted child collects observations; expected results and verdicts stay on the host. The caller checks the freeze before and after execution. Receipts bind source, ordered scenarios, evaluator, runtime/image, limits and independent-acceptance purpose. An execution intent with an ambiguous outcome is retained rather than quietly rerun until it passes.

A separate Playwright adapter exercises actual browser controls for intake, progress, cancellation/reload/retry/commit, search, literal text rendering and export requests. Candidate Python and its HTTP server remain in a networkless Docker container; Chromium runs in a fresh sandboxed host context. Bounded same-origin browser requests are routed through a trusted Docker-exec loopback client, with other origins and unsupported transports rejected. This is a routed browser-transport observation, not qualification of a normal published host port or a claim that all candidate code runs inside Docker. Browser traces, screenshots, request evidence and cleanup outcomes must accompany its result.

The prospective public addendum M1-UI-AUTOMATION-V4, defined in peer_library_contract_v4.py, makes the browser's automation interface available to every builder, selector and reviewer before live work. It specifies accessible labels and roles, complete job identity, state/epoch/progress values, action names and literal domain-error codes. The intake combobox name may start with Intake type, allowing a wrapping label; unavailable actions may be absent or disabled. The browser driver must match complete bounded job tokens and clear its own earlier search before expecting unfiltered results. HTML IDs, CSS, layout and element nesting remain implementation choices.

Publishing these requirements prevents a browser evaluator from imposing undisclosed naming or structure criteria after models have finished. The addendum does not reveal private scenario inputs or expected outcomes, and it does not rewrite the frozen historical product specification. Its prompt and evaluator changes require qualification under the new execution design before live use.

These checks cover the declared M1 surfaces. They are not the four-milestone project's complete acceptance suite, an untouched application family, or evidence of multi-host Byzantine safety. Independent expectations reduce evaluator coupling; a finite suite still cannot prove the absence of every defect.

The larger obligation remains

The large-swarm project plan still requires M1 ingestion, M2 document lifecycle, M3 recovery/portability and M4 compatibility and operator handoff. Its first comparative cohort has six complete trajectories: S4-G with eight roles, S16-G with twenty and O16-G with twenty, each in a healthy and a predefined recovery block. All use the same gossip transport, matched offered resources and a whole-six-trajectory freeze before private evaluation.

This central healthy M1 development pilot does not fill a registered comparative cell or silently narrow that goal. Peer-local work selection, model-selected high-signal executable tests, the full restart/partition schedule and cumulative milestone preservation still need implementation and qualification. The separate decision-placement × transport comparison and untouched project families remain necessary for stronger causal and general quality claims. Scaling beyond twenty roles should follow a demonstrated useful work frontier and measured review and integration capacity, rather than increasing the role count alone.
