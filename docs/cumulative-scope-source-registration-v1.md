# Source-derived scope registration

This layer loads the actual cumulative v2 sources and the separately retained ownership review, rederives executable assertion selectors, and installs a complete acceptance registration only after the compiler and an independently delivered full semantic review agree. It does not supply that review, a complete production ScopePlan, prerequisite qualifications or product observations.

`cumulative_scope_source_v1.load_catalog` retains all 123 product requirements, three prerequisites, 312 source units, 22 authority rules and 188 planning-gap notes. The 57 shared owner decisions retain their actual citations and interaction owners. That ownership review does not approve applicability. The 12,975 eligible kind/lane cells are an unapproved cross-product requiring decisions, not 12,975 automatically mandatory tests.

The closed `cli_slice`, `http_slice` and `product_process_slice` factories take the real typed prospective executor registrations. They reconstruct the original purpose, complete ordered cases, source/evaluator identity and concrete observation pointers. Replacing a dataclass digest or case label cannot add evidence. CLI retains all 900 diagnostic cells, including 32 unspecified cells; the process catalog retains its 33 unspecified facets. Raw captures, lifecycle mechanics and unasserted values are not promoted into state evidence. Product-process state/byte claims do not use JSON syntax alone; CLI syntax selectors do legitimately address the separately specified JSON/channel contract. An assertion declares the selected subfacet only. A natural exit demonstrates invocation, not the command's effects; a parsed value does not prove SQL layout, atomicity, original stored bytes, abrupt recovery or browser behavior.

`assemble_declaration` always emits all 312 obligation plans. `scope_review_input` populates only the concrete proposed assertion cells and retains all 188 source notes. It invents no N/A, purpose waiver or compatibility override. Every other eligible cell remains unresolved. `coverage_census` reports that distinction; a unit with an assertion is not a fully covered unit. These functions produce review inputs, not semantic approval or a runnable full-study scope.

`ScopeSubmission.request()` includes original source values, all plans/cells/selectors, 22 authorities, 188 notes, 99 logical purposes, suite definitions, compatibility and the four-milestone/six-trajectory design. It also binds the current implementation sources. An earlier component-review reference inside a declaration is separate from the subsequent whole-request review, avoiding a circular review hash.

`ScopeRegistrationController` requires an actual `CheckpointChain`, durable `ExternalHead` and independently obtained expected prefix. `stage` retains the prospective request. Trusted host configuration separately enrolls the identity of an independently delivered original report and its delivery provenance. The original report must have an exact ordered decision for every review target, with inspected references and rationale. Wrong purpose, omitted/reordered decisions, rejected or unresolved findings, changed source owners and substituted selectors prevent registration. Request, report, delivery and registration must appear in that order in the authenticated chain, including on replay.

This enrollment is an explicit trusted-host provenance boundary. Hashes authenticate bytes and linkage; they do not establish reviewer identity or semantic competence. Candidate-provided JSON, a passed flag or fabricated test enrollment grants no production authority. Tests using invented reviewer originals qualify only this mechanism. The currently incomplete real source declaration cannot register successfully, and the successful complete production registration path has not yet been exercised.

`ScopeSnapshot.registration()` and `registration_provenance()` reauthenticate the exact original request, review, delivery, registration and current source. The provenance accessor exposes receipt names, hashes and one-based positions within a single chain context. It does not prove registration preceded a candidate execution in another journal. A composite controller must retain and authenticate that cross-journal pre-dispatch link, the exact six final sources, actual final stop barrier and fresh independent/repeatability executions. Prerequisite, observation, freeze and promotion methods in this registration-only authority remain explicitly unavailable.

The new product-process executor dependency required a local correction from the unsupported `product/` source namespace to canonical `gossip_harness/`. The original contributor source and the observed failure are retained. The earlier product-only passing receipt is not qualification of this corrected integration. Root owns final integration and combined verification; no Docker, provider or candidate execution occurs here.
