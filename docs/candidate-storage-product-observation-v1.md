# Final-M4 storage and intake observation draft

This version adds a fresh execution path for the existing eight B01 and 241 B02 histories. It does not relabel their earlier qualification receipts. The prospective profiles preserve the original `harness_qualification` definition purpose and explicitly bind a newly requested `public_release`, `independent_acceptance`, or `repeatability` execution. No candidate execution, independent production source review, or complete semantic ScopePlan accompanies this draft.

`candidate_storage_product_profile_v1` reconstructs the fixed per-history assertion census from authored expectations, never from a candidate's returned job set or selected branch. B01 has 92 diagnostic selectors, including 60 proposed normative inherited selectors and 32 unqualified auxiliary selectors. B02 has 6,215 diagnostic selectors: 5,756 proposed normative inherited selectors, 456 unqualified selectors, and three explicitly unspecified error-code selectors. These counts describe declarations, not approved semantic coverage. The fixture-specific auxiliary schema projection is not reused as a general candidate expectation. Every newer schema4, generation, control, recovery, migration, worker, backup and other full-project obligation remains mandatory.

`StorageReviewAuthority` consumes a real controller-owned CheckpointChain and independently expected ExternalHead prefix. Protected host enrollment identifies the original request, reviewer report and independent delivery; every read checks those original bytes and request-before-report-before-delivery order. The request contains the complete declared profile and exact common/native source, Git, layout, schema and purpose identity. The host must actually establish reviewer provenance and substantive inspection of the complete source and persisted representation. A matching digest or a synthetic enrolled test report does not establish those facts. The authenticated review origin, including its independent prefix and original positions, is bound into the execution configuration and prospective binding. This limited review is separate from complete project semantic scope approval.

`CandidateStorageExecution` captures the registered complete Git tree, independently reconstructs the new binding, and requires that concrete review authority plus ObservationAdmission. Fresh independent and repeatability purposes require the exact irreversible six-trajectory freeze. The owner retains a one-shot intent under an externally anchored compact journal; a retained incomplete intent cannot dispatch again. Every ordinary command, persistent session, phase request and successful session-finish request checks admission both before retaining its intent and again after checkpoint acknowledgment. Physical effects validate the original Engine endpoint. Each phase retains original runtime boundary evidence and strict regular-file/directory checks of the source and helpers, plus the exact fixture census. A final staging check is required by the mechanics guard.

The fixed child adapters import candidate code only inside their fresh container. They receive operations and fixture definitions, not host expectations or verdicts. B02 ordinary recipes have a new invocation entry point; the old closed qualification reviews remain frozen. The five forced-schedule histories execute their explicit unavailable path until a separately versioned, actually qualified candidate instrumentation mechanism exists. They are neither waived nor counted as passing concurrency evidence. The snapshot still follows an API response, and Store close/reopen remains within one persistent adapter process. This is not atomic method-return capture, process-death, crash recovery or arbitrary concurrent-write evidence.

All original streams and tar captures are retained. The 40 MiB capture bound is preserved through independently hashed 16 MiB chunks when a single stream exceeds the journal's per-file bound. The new owner has exception-safe local subprocess/reader teardown. Cleanup uses the existing separately owned emergency channel and only acknowledged resource claims after journal uncertainty. Its outcome never heals the execution journal or upgrades acceptance. A failed or uncertain cleanup keeps the mechanics outcome incomplete.

`candidate_storage_product_observation_v1.reconstruct` reparses original response and tar bytes through the authenticated owner, applies the reviewed raw-layout mapper, and emits every declared diagnostic. It distinguishes missing observations, unsupported mappings, explicitly unspecified assertions and known failed comparisons. An authenticated later phase with changed process identity, fixture labels or runtime/staging attribution is unavailable for semantic capture; it does not erase an earlier established failure. Tampered journal bytes or substituted command identities invalidate the evidence. The current sandbox checks retain the bounded command configuration and narrow snapshot identity checks; complete created/prestart sandbox-admission qualification is still a separate required evaluator obligation.

`publish_verifier` retains a host-derived verifier in the same chain. `StorageObservationSource` requires the exact physical owner and independently expected post-publication prefix, then reconstructs the facts again and compares the original verifier. A fixture owner or caller-uploaded StorageExecution dictionary cannot become a Registry observation. Incomplete originals use an explicitly identified durable-intent basis and `infrastructure_error`, preserving attributable failed cases; they cannot become complete passes. Verifier identity is stable across the append, while the independently supplied full current prefix remains authoritative on every consumption.

`selector_catalog` exposes concrete `/projection/checks/...` pointers, original raw dependencies, authored partial source-unit facets and a separate mechanics guard. The held complete-scope source factory does not yet recognize this family; adding it requires a versioned integration and independent full-denominator review. No new factory claims complete clauses from a lone partial selector. All 123 product requirements, three prerequisite gates, 312 source units, 22 authority rules, 188 gap notes, four milestones and six trajectories remain in scope.

Adding these 249 histories to the earlier 341 yields 590 proposed public-purpose physical slots before independent acceptance or repeatability. That is an explicit prospective capacity/qualification dependency, not a reason to truncate histories or silently split an execution.

They exercise admission and retention mechanisms; they do not establish a real source review, Docker execution, full production registration, project completion or swarm-quality result. The new physical executor and combined controller integration still require root-owned static/offline reconciliation, representative deliberate-defect controls, the appropriate full physical catalog, original evidence audit, and the complete changed-contract rehearsal before live study use.
