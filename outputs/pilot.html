The project has a concrete finish line

The fixture is a small Python 3.12 command-line application named task_report. Given a UTF-8 CSV task list, it must print a JSON summary. The CLI already exists; workers implement the two missing modules. Only their assigned paths may change.

TaskAllowed fileContract
CSV parsertask_report/parser.pyParse strict CSV with exact id,title,status,estimate headers. Support quoted values, trim data fields, reject duplicate IDs and invalid records, preserve input order, and return exact typed records.
Summarytask_report/summary.pyCount todo, doing, and done; sum total and remaining estimates. Return integer values, preserve inputs, and keep calls independent without shared mutable state.

A correct project must also work through the supplied CLI: valid input produces JSON and exit status 0; invalid input or an unreadable file produces an error and exit status 2. External checks cover 13 parser cases, 6 summary cases, and 4 CLI integration cases: 23 checks in the complete acceptance suite.

Boundary cases and the immutable contract

The parser requires a header, exactly four cells per data row, nonempty IDs and titles, case-sensitive uniqueness after trimming, and statuses drawn from the three exact allowed strings. Estimates are nonnegative ASCII decimal integers; leading zeros are valid. Quoted commas, escaped quotes, quoted newlines, empty physical records, malformed records, and late failures are checked. The summary must return fresh output with integer values, including zeros, without mutating its input or accumulating state across calls.

The contract is task-report-v1. The run manifest binds the initial project files, acceptance-check hashes, pinned Docker image, model, and fixed arm roster. A successful rehearsal for older inputs or checks cannot authorize the current live run.

The single-worker arm changes task packaging as well as integration structure. The two maintainer arms hold those choices constant and change the modeled transport. One run per arm is far too small to establish a reliable quality or cost difference, especially with variable model output.

This is not yet the original semantic-sharing experiment. Gossip carries proposal announcements to integration gates. Coding workers receive assigned tasks, files, and local validation feedback; shared discoveries do not yet change their plans. This pilot tests the connected coding workflow, not whether gossip-driven exchange of insights improves project completion.

  1. The dispatcher claims the fixed tasks and reserves budget before a generation request. Lease heartbeats keep staged attempts valid while other work and checks run.
  2. The worker receives the task contract, allowed paths, current files, base commit, and any local failure feedback. It returns a structured patch. The harness enforces output shape and file scope.
  3. A private candidate runs through the relevant checks. On a local failure, the worker may receive feedback and try again, with a maximum of two generation attempts per task. A repair remains inside the original file scope.
  4. Successful module proposals feed the combined integration tree. The full project must pass before release; partial module success does not complete the project’s ledger tasks.
  5. A durable publication intent names the exact candidate and task attempts. Git compare-and-swap and ledger recovery preserve the accepted commit and ownership boundary.

Validation runs in the pinned official Python image, as a non-root user, with no network, a read-only root filesystem and mounts, dropped capabilities, process/memory/CPU limits, and bounded execution. The container receives copied project files and trusted external checks; it does not receive the host workspace or API credential. Isolation and timeout cleanup are exercised with actual Docker runs.

Local validation failures can trigger bounded repair. A failure of the final combined project remains a failed project in this pilot; it does not start an open-ended autonomous debugging loop. Ambiguous requests are not automatically replayed.

A shared $10 ceiling, with conservative accounting

The user authorized $10 total across the first live trial, shared by all three arms. The ledger uses integer microdollars: one million units per dollar. Every generation request first reserves $0.336864, covering a full 400,000-token input context and the configured 8,192-token maximum output at standard rates.

The pinned model is gpt-5.4-mini-2026-03-17. Standard rates verified on September 30, 2026 are $0.75 per million input tokens and $4.50 per million output tokens. The official model documentation is the pricing and capability reference used for this pilot.

After a response with known usage, the ledger settles using reported token counts and those rates, rounded upward to microdollars. Cached input is conservatively priced as uncached; output usage includes reasoning tokens. Unknown usage keeps its reservation and stops the affected execution path. These are conservative harness charges, not a provider invoice or a measured total cost of running the computer.

Final ledger: 8 generation reservations, none unsettled, 35,885 microUSD accounted ($0.035885), and 9,964,115 microUSD remaining under the $10 cap ($9.964115). All five logical ledger tasks completed, with no pending publication intent. The earlier read-only model lookup verified authentication.

What this smoke test establishes

Real model output traveled through owned tasks, isolated Git proposals, external validation, bounded repair, and the exact-release gate. The observed repairs also exercised feedback under real model behavior. This establishes a working practical path; it does not establish that gossip, multiple workers, or delegated maintainers outperform a simpler design.

The next useful experiment needs broader repository tasks, dependency and cross-task evidence, and repeated matched-budget trials. Workers should receive relevant shared discoveries and demonstrate how those discoveries changed a plan or avoided duplicated work. Keep strong single-worker and orchestrated baselines, hold task-generation policy and acceptance rules constant where possible, and measure accepted requirements, regressions, rework, usage, and completion time.

That is the point at which the original gossip hypothesis becomes testable. If a shared event store supplies the same benefit with lower cost and complexity, it remains a valid outcome.
