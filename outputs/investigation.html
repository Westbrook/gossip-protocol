What the Linux model gives us

Linux development distributes repositories and development work while retaining a chain of maintainers and an authoritative mainline. This is federated, hierarchical integration authority; it is not leaderless consensus about conflicting code. A contributor can propose a change from an independent repository; a receiving maintainer decides whether to pull it. Git explicitly documents this integration-manager and lieutenant pattern. Repository hosting is a separate choice: the same workflow can use GitHub, a private Git server, or local repositories. Git’s distributed workflows and the kernel development process support this mapping.

The useful distinction is between proposing work, accepting a subsystem change, and accepting a release. A linux-next-like integration tree combines prospective changes to expose interactions before release. That integration tree is disposable; it should not become an accidental base for future worker development. Git’s workflow manual describes topic branches and disposable integration branches, and the kernel’s merging guidance explains the care required with shared prerequisites and already-published history.

It helps

Independent work, exact provenance, selective adoption, restartable proposals, and clear responsibility for each integration decision.

It still needs

Project-level acceptance tests, dependency contracts, ownership rules, and a way to decide between incompatible changes.

It costs

Additional integration stages, maintainer queues, more repository state, and repeated verification. Small projects may need only one integration gate.

A successful textual merge does not establish that the application still behaves correctly. A subsystem maintainer narrows the decision and its owner; it does not remove the need to detect and resolve conflicts.

  1. A scripted worker creates a focused proposal in its own Git repository, identified by immutable commit IDs.
  2. An immutable event advertises the proposal manifest and evidence. Recipients explicitly fetch the relevant Git history when they need it.
  3. The responsible gate examines a candidate privately and runs the relevant validation against that exact candidate.
  4. The gate accepts the tested commit only if the accepted branch still has the expected old head. A competing update invalidates this attempt rather than silently accepting a different tree.
  5. In the maintainer topology, subsystem acceptance is followed by a combined integration gate and release acceptance. Global acceptance may fail even when each subsystem passed.

Evidence must name the proposal’s base and candidate tree, plus the test-recipe version and execution environment. A result from a different base, a superseded check, or an incompatible environment cannot automatically approve the new combined tree. The local fixture gate already validates the exact candidate it promotes; portable, versioned test/environment receipts remain a requirement for a future live-agent runner.

Proposal scope is checked against inherited history as well as the visible tip change. A worker cannot import unaccepted sibling-subsystem changes merely by making a final commit that touches only its own files. Kernel maintainers confront the same shape of dependency problem; their guidance favors focused prerequisite branches over importing an entire sibling tree. Kernel rebasing and merging.

Git already supplies the object-transfer machinery. Local-path fetches are enough for this milestone; later versions can use approved SSH/HTTPS remotes or Git bundles. A proposal announcement is a claim to inspect, never permission to update the accepted release.

Separate integration topology from transport

Four scripted scenarios run under all four combinations below: 16 cases per seed. Worker edits, proposal order, acceptance rules, and repair policy are held constant. This isolates integration ownership from evidence delivery; it does not yet test autonomous scheduling.

The broker baseline has one leaf–broker exchange per leaf per synchronous tick. Leaf-to-leaf delivery needs ingress and egress rounds. Gossip uses bounded-fanout push-pull exchange. These are connectivity and dissemination models; their contact counts are not bytes, socket operations, tokens, or production event-bus performance.

The semantic fixture is the key conflict test. 6 + 6 > 10 is not a Git merge conflict. Each contribution can look valid alone. A combined-tree invariant is what prevents an invalid release.

Every prepare attempt and validation call counts, including maintainer, combined-integration, and release stages. Fewer proposals reaching the root do not automatically mean less total work. Fixed processing order intentionally waits for notices; delivery timing does not choose which task runs next in this matrix.

The semantic case confirms the important boundary: both subsystem allocations of six can pass local checks, yet the combined twelve-unit allocation fails. The release retains the first valid allocation. The maintainer structure assigns responsibility and catches the interaction; it does not make individually valid changes compose automatically.

The small fixtures also expose the hierarchy’s overhead. Independent edits require five validation calls through maintainers versus two at one gate. That does not rule out a benefit on large modular projects, but it prevents claiming that delegated integration is automatically cheaper.

Ownership, budgets, and interrupted publication

The task ledger and promotion bridge are tested separately from the fixed-order matrix. The ledger provides transactional claims, fencing epochs for superseded attempts, dependency checks, reserved integer credits, and durable publication intents. The credits demonstrate bounded reservations; they are not a dollar-cost model. Expiring a lease does not automatically refund work already in flight.

SQLite and Git do not share a transaction. The publication bridge first records an intent that names the task attempts and exact candidate, then performs the Git compare-and-swap, then finalizes task state. Recovery inspects accepted Git ancestry to distinguish a published commit from an unpublished or stale attempt. A local operating-system lock prevents recovery from canceling a publication that is still active.

This protocol assumes accepted-ref writes pass through the harness. Out-of-band force updates and cross-host failover are outside its current guarantees. The task ledger is not yet a live scheduler driving the topology matrix.

Component checks and independent stress review

Verified component checks include 16 Git-backend tests, 16 transport tests, 11 ledger tests, and seven publication/recovery tests across the completed suite and focused regression runs. Independent probes completed 160 constructors across 20 fresh databases, bounded 30 concurrent one-credit reservations to a ten-credit cap, kept duplicate reservations idempotent, and accepted four concurrent replays of the same promotion exactly once at the task level. The completed 16-case matrix also passed seven experiment assertions. In total, 57 unique harness tests were covered across component and experiment runs; CLI inspection and Python compilation checks passed. The earlier dissemination simulation is separate from this count.

Review exposed two issues that were corrected: concurrent first-startup schema initialization, and retrying an unpublished intent after a pre-Git crash. The fixes serialize initialization and permit a fresh publication generation for rejected, unpublished attempts. These checks concern the trusted local runtime, not multi-host distributed consensus.

The next experiment should earn the complexity

My current assessment is that this hybrid is promising for modular projects with clear subsystem boundaries and strong acceptance tests. Gossip dissemination and hierarchical integration authority are compatible. Independent subsystem test passes still cannot prove combined semantic consistency, and the scripted fixture comparison must be interpreted as a test of these mechanisms rather than a software-productivity result. It should be evaluated first with a shared worker runner, the same repository tasks, a fixed total budget, identical acceptance tests, and explicit integration ownership. Keep the broker-versus-gossip comparison as a separate variable. Include a strong single-agent or orchestrated baseline rather than treating a poorly designed coordinator as the competitor.

  1. Connect the tested ledger and publication bridge to a real task dispatcher, and verify that retries and failures preserve ownership and budget rules through a whole run.
  2. Add provider-neutral coding workers and reproducible patch-generation tasks. Pin model, runner, tool access, task inputs, and review rules before comparing results.
  3. Measure accepted requirements, regressions, review/rework, total cost, completion time, and recovery. Count every maintainer and verification step.
  4. Introduce separate hosts and actual network failures only when a real deployment requires them. Add authenticated identities and permission boundaries before accepting untrusted peers.

If a shared-state or broker-based design produces equivalent accepted software for less cost and complexity, that is a useful result. The immediate objective is a reliable harness and an honest comparison. Any new protocol should emerge from a demonstrated gap.
