Gossip protocol / research memo / September 29, 2026

Share discoveries.
Keep commitments explicit.

Gossip can be a useful layer in an agent harness. The case for replacing project coordination with an entirely leaderless swarm is much weaker.

Recommendation: build a comparative research harness. Start with four to eight coding workers, structured evidence, isolated workspaces and a reliable integration gate. Make gossip a replaceable communication mode. Expand only if it beats a strong orchestrator and a simpler shared event bus on accepted software per dollar, completion time, or realistic failure recovery.

This memo distinguishes published evidence, vendor reports, implementation claims and our engineering recommendations. It proposes a harness; no live LLM harness or paid agent experiment has been run. The accompanying local simulation measures information spread only.

The reference: what it establishes

I accessed Anjan Biswas’s public MURMUR video post, inspected its visuals and read its full transcript. The post presents a simulation-based concept rather than a demonstrated coding harness. Its useful mechanisms include digest exchange, on-demand detail retrieval, evidence and refutations, semantic plus random peer selection, and preserving conflicting claims. Its six-round/1,000-agent and eleven-round/million-agent illustrations are dissemination results, not project-completion results. I did not find simulation code linked in the visible post, so its specific measurements are not independently reproduced here.

Four distinctions change the conclusion:

  1. Delivering a claim does not make it true. A hash establishes the identity of some bytes. A signature identifies a producer. Neither establishes that the referenced test ran correctly or that the conclusion follows.
  2. A scalable coordinator does not read every worker’s transcript. Queues, indexed artifacts, hierarchical planners, subscriptions and durable checkpoints allow summaries to reach the appropriate decision maker. An overloaded single context window is a weak baseline.
  3. Bounded outgoing fanout is not bounded total work. Incoming contacts, document pulls, verification, storage and agent reasoning still cost resources. If every worker must consume every other worker’s discoveries, total useful deliveries grow quadratically with the worker count at a fixed per-worker production rate.
  4. Faster refutations are a policy to implement and test. Priority queues and tombstones can help, but partitions, false evidence and already-triggered actions prevent a general guarantee that corrections always win.

Classic epidemic algorithms address replica update propagation; SWIM separates membership dissemination from failure detection. Neither provides an automatic solution to project planning. The distinction is present in the original Demers et al. paper and SWIM paper.

Local dissemination probe: fast spread, repeated contacts

With 1,000 nodes and 100 seeded trials, synchronous push reached everyone in a median of 8 rounds (95th percentile: 9); push-pull took 5 rounds (95th percentile: 5). Each node contacted 3 distinct random peers per round. Median contact totals were 24,000 and 15,000 respectively, including uninformed callers and redundant contacts.

At 10,000 nodes over 20 trials, full-spread medians were 10 rounds for push and 7 for push-pull. This supports rapid spread under the stated model. It does not reproduce the video’s simulator or test a million peers.

One immutable fact; complete connectivity; synchronous snapshots; no within-round cascades, failures, bandwidth limits, verification or LLM reasoning. An ideal star needs 999 deliveries for 1,000 nodes in one hop, assuming the fact starts at the hub and hub concurrency is unlimited. Full-duplex contacts and star deliveries are different units; neither is a token-cost estimate. The star is an illustrative topology baseline, not a measured production broker.

Broader evidence reinforces the need for a controlled experiment. Kim et al., version 3, April 2026 studies 260 configurations across six benchmarks and finds strong dependence on task structure and baseline capability. Its software subsets are small and comparisons are underpowered; its decentralized condition is all-to-all debate, not epidemic gossip. It supports caution, not a universal verdict.

Cursor’s July 2026 follow-up adds shared design documents, explicit decision ownership, a neutral merge-conflict agent and agent-maintained operating guidance. It reports better results with a revised harness and candidly describes its earlier browser as far from polished software. This is stronger support for improving context and coordination than for eliminating structure.

Public documentation and papers were reviewed; third-party implementations were not installed, audited or independently benchmarked. “No controlled benchmark found” describes this search, not proof none exists. Primary-source engineering reports can select favorable examples; preprint results may not replicate.

The strongest positive case

Consider a library migration across thirty relatively independent packages. One worker discovers that a new API treats timeouts differently, attaches a minimal failing test and identifies affected symbols. Only relevant workers retrieve the evidence. They can reuse a verified finding without a planner rewriting it into every assignment. Repeated recovery from worker turnover can also become cheaper when discoveries are durable and replicated.

This is valuable even if a shared event bus turns out to deliver it more simply. The economic opportunity is reducing repeated investigation and context reconstruction. The protocol is a means to that outcome.

The strongest negative case

Now consider a feature that changes authentication, storage, API semantics and UI behavior simultaneously. Six agents can receive the same requirements and still choose incompatible designs. Passing six local test suites does not prove the integrated feature works. Fast gossip can make all six consistently wrong sooner.

Software dependencies also bound parallelism. A worker cannot use an API whose meaning is still undecided. More agents can add contention to the critical path. At four to eight workers on one machine, communication bandwidth is unlikely to be the primary bottleneck; this is a hypothesis to measure in traces, not an assumption that justifies a network rewrite.

Three invariants we should not confuse

ConvergencePeers eventually hold the same events.
TruthThe events and conclusions correspond to reproducible evidence.
CompletionThe integrated project satisfies the requested behavior.

CRDTs can help with the first. They do not provide the other two. Majority votes from similar models are not independent evidence. Keep original evidence IDs so ten forwards of one faulty observation still count as one observation.

A useful theoretical guide is CALM: monotonic computations admit coordination-free consistent implementations under its model. Adding immutable observations fits that direction. Exclusive task ownership, revoking permission, consuming a fixed budget and declaring no required work remains involve decisions that need stronger treatment. This is a design inference, not a theorem proving our whole harness correct.

A harness worth building

Use two connected layers: decentralized evidence exchange and an explicit authority for commitments. The authority can be ordinary deterministic code. It does not require a language model to approve every step.

  1. Project contract. Store versioned requirements, explicit non-goals, interfaces, acceptance tests and the total budget. Start with a human-approved scope; an agent can propose revisions, but a rumor cannot silently change the contract.
  2. Replaceable worker runner. Launch existing coding agents through a common adapter. Each task gets a sandbox, separate Git worktree, resource limits and a pinned base commit. Capture model, tool, token, timing and artifact records. Avoid writing a new coding assistant and a new transport simultaneously.
  3. Task ledger. A transactional queue records task dependencies, owner, attempt, lease epoch and status. Workers may choose ready work themselves. Lease renewal and release are deterministic harness operations. A stale worker may keep computing but cannot land results after its epoch has been superseded.
  4. Evidence store. Content-addressed immutable artifacts include test logs, minimal reproductions, patches and relevant source snapshots. Assertions carry their scope. “Test T passed at commit H with environment E” stays true as a historical observation; “main is healthy” can become stale immediately.
  5. Evidence exchange. Compare a reliable pub/sub implementation with a gossip implementation behind the same interface. Peers exchange IDs, versions, topic tags and bounded summaries; fetch details only when useful. Use original bytes, not another paraphrase at every hop.
  6. Verifier and integration gate. Run trusted test recipes against the candidate integrated tree. Preserve regression tests separately from agent-editable code. Check the current task epoch and base revision, update the accepted head atomically and invalidate obsolete evidence. An LLM reviewer can find semantic defects, but cannot replace executable checks or explicit approval for product decisions.
  7. Observer. Reconstruct who knew what, why work was claimed, why a candidate was rejected and what it cost. It can display the whole project without being the controller. Store full evidence outside model context.

This is deliberately a hybrid. A fully decentralized design could distribute the authority using consensus, escrow or partitioned ownership, but that is another problem. Gossip alone does not solve it. On loss of authority, workers may continue reversible local investigation within previously reserved budgets; merges and new commitments wait.

A2A already supplies concepts for agent identity, tasks, messages and artifacts. Reuse compatible formats where useful. Protocol novelty should be a consequence of demonstrated gaps—especially commit-scoped evidence and invalidation—not a prerequisite for the first experiment.

Protocol sketch: observations, not ambient authority

This is a proposed internal contract, not a new claimed standard. Begin in one trust domain with known workers and explicitly configured repository access.

{
  "schema": "evidence.v0",
  "event_id": "hash-of-canonical-payload-excluding-id-and-signature",
  "kind": "observation | hypothesis | refutation",
  "project_id": "project-17",
  "producer_id": "worker-3",
  "producer_sequence": 42,
  "causes": ["prior-event-id"],
  "scope": {"repo": "repo-id", "commit": "full-sha", "paths": ["api/"]},
  "environment_hash": "toolchain-dependencies-config-and-recipe-fingerprint",
  "topics": ["payments", "timeout-contract"],
  "claim": "Named timeout test fails under the candidate API",
  "evidence": [{"artifact_hash": "...", "test_recipe_id": "timeout-v2"}],
  "supersedes": [],
  "expires_at": "timestamp-for-routing-and-revalidation",
  "origin_signature": "optional-in-local-v0; required-across-trust-boundaries"
}

Compute the event ID from a canonical serialization excluding event_id and origin_signature; sign that digest. Specify the canonicalization and hash algorithm before interoperability testing. The environment fingerprint identifies the toolchain, dependencies, relevant configuration and recipe version used to produce executable evidence.

Do not turn this envelope into a remotely executable command format. Test recipe IDs resolve through trusted harness configuration. Evidence text, issue descriptions and source files remain untrusted input; policy enforcement lives outside the LLM. Treat artifact URLs as access-controlled references, not arbitrary instructions to fetch or execute.

Details that make or break the implementation

  • Sampling: begin with a small random peer set and topic filters. Semantic neighbor selection is an ablation, not an assumed improvement. Retain random exploration to avoid isolated clusters.
  • No LLM heartbeat: hashing, deduplication, scheduling, synchronization and most relevance filtering run in normal code. Wake a model only for actionable novelty or a task.
  • Evidence grades: distinguish reported observations, independently reproduced results and untested hypotheses. A second model agreeing is not the same as a second isolated test run.
  • Staleness: use commit identity and dependency changes before arbitrary wall-clock TTLs. Preserve expired evidence for audit while excluding it from current decisions.
  • Deletion and repair: retention rules must retain refutation/supersession records long enough for offline peers to catch up, or force those peers to resynchronize from a checkpoint. Do not garbage-collect tombstones casually.
  • Hard budgets: reserve per-worker credits transactionally before calls. Eventually consistent global spend counters cannot enforce a strict cap. Include retries, reviews and failed candidates in the budget.
  • Duplicate work: prevent accidental duplication with claims, but permit explicitly budgeted independent attempts for uncertain problems. Do not spread a tentative answer so early that all attempts become copies.
  • Termination: declare completion only when the authoritative required-task graph and the accepted integrated head satisfy the versioned contract, with no outstanding required work. A silent network is not completion.

A good first failure scenario is a worker returning after its lease expired. Another worker has already completed the task on a newer base. The old worker’s observation remains historical evidence; its patch submission fails the fencing/base checks. That is the kind of correctness guarantee to test before inviting more agents.

Build the experiment before the ecosystem

There are two causal questions: does distributing decisions help, and does gossiping evidence help? Changing models, memory, task prompts, verification and communication simultaneously cannot answer either.

VariantDecisionsInformation delivery
A · Strong single agentOne agent; durable checkpoints and the full budget.Same artifact access and retrieval.
B · OrchestratorDynamic planner plus workers; restartable coordinator.Reliable event bus and scoped evidence.
C · Shared boardWorkers choose ready tasks; common authoritative gate.The same reliable bus and evidence representation.
D · Gossip hybridExactly the same work selection and gate as C.Bounded-fanout gossip, on-demand pulls and repair.
Optional EThe same orchestrator as B.Gossip evidence delivery: completes the topology/allocation factorial comparison.

D versus C is the critical comparison for gossip. Both use the same task-generation policy: workers can propose tasks and dependency changes, admitted through the same versioned ledger rules. The natural B versus C comparison changes the overall coordination policy, including planning. Add a fixed-task-DAG ablation, with identical tasks and dependencies in B and C, to isolate dispatcher assignment versus worker self-selection. B versus A tests whether a team helps. Give every variant the same benefit from structured evidence and durable artifacts. Otherwise an information-format improvement will be misattributed to transport.

Workload and controls

Start with 12 repository tasks, two runs per variant: 96 capped attempts across A–D. This is a screening study, not enough to establish general superiority. Use the observed variance and practical effect size to choose the follow-up sample size; include held-out repositories and task classes. Separately include a small set of complete multi-feature projects so passing isolated issues cannot masquerade as project delivery.

Include independent fixes, package migrations, coupled API/UI features, sequential debugging and architectural ambiguity. Pin repo snapshots, model identifiers, tool versions, prompts, containers, tests, worker counts and limits. Interleave variants to reduce provider-load drift. Use hidden acceptance tests plus blinded human review of correctness and maintainability. Worker-generated tests can supplement but cannot redefine the evaluator.

Run an equal-total-dollar comparison first. Run a separate equal-deadline, matched-concurrency comparison if the operational aim is speed. Count planning, communication input tokens, summaries, verification, failed runs, conflict repair, cached tokens and human rescue. Report cost for the entire cohort divided by accepted outcomes so failures are not dropped from the denominator.

Measures

PrimaryAccepted project completion under the budget; total cost per accepted outcome.
Quality constraintsRegressions, severity, maintainability, human review/rescue time.
DiagnosticsDuplicate work, stale decisions, context cost, idle time, merge repair, delivery lag.

Fault injection should cover dead workers, coordinator restart, duplicate and out-of-order messages, short partitions, stale commits and a false claim with invalid evidence. Give the orchestrator baseline durable recovery. Give each variant comparable faults in the components it actually has. Confirm that work can continue locally without allowing stale merges or budget violations.

Proposed continuation and stop criteria

  • Before measured runs, choose one primary benefit: for example, at least 20% lower total cost per accepted outcome, with a predeclared small quality non-inferiority margin. Estimate paired uncertainty clustered by task/repository; an inconclusive interval means inconclusive.
  • If speed is the intended product value, predeclare a separate target such as 25% lower completion latency at a matched budget. Do not switch the primary metric after seeing results.
  • Continue the gossip layer only if D improves on C in the intended workload or provides material recovery benefits under failures users actually encounter.
  • If C matches D, keep the simpler shared-state implementation. If the strongest single agent wins, reduce the team architecture. Either outcome is useful.
  • Stop and repair invariant violations immediately: stale workers landing changes, hard budget overshoots, unauthorized evidence disclosure, or unverified completion. Do not trade these away for throughput.

These thresholds are proposed engineering gates, not conclusions from published studies or user-approved spending limits. A dollar cap and runner choice must be set before any paid benchmark. No spend has been initiated by this research.

For one experienced engineer reusing an existing coding runner, I would budget roughly two to four weeks for a credible local pilot, depending on runner integration and evaluator quality. That is an estimate, not a delivery promise. Production resilience, multi-tenant security and cross-organization participation are a substantially larger effort and should be separate milestones.

The initial implementation can be Python with a local transactional store and JSONL traces. A small single-host ledger does not need a cluster. Git and containerized test runners provide artifacts and isolation. Keep transport replaceable; investigate reusing agent-gossip or another mature P2P layer only when actual remote peers justify it.

My honest judgment: there is enough here to justify a bounded experiment. There is not enough evidence to justify investing first in a universal leaderless protocol. The likely useful result is a disciplined team of agents sharing versioned evidence, with gossip earning its place through measurement.
