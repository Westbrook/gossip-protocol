What the scouts actually contributed

Eight scout requests supplied 12 admitted cases. The admission log contains seven rejection entries: three malformed whole-response batches, three parsed proposals with wrong expected answers, and one out-of-domain parsed proposal. Seven entries therefore does not mean seven individual rejected tests. Trusted host-oracle filtering remained a material advantage of this experiment.

The 12 admitted cases produced 16 probe-by-stage executions, all passing; retained revalidation is not a new admission. The admitted cases did not trigger an observed failed-check repair. There were no repairs in either policy, and all final gates passed. This does not exclude a preventive effect from showing tests before implementation, but it provides no measured incremental defect catch or quality improvement. More admitted tests alone is not evidence of more correct software.

Admission also does not prove that a case exercises its claimed requirement. One case labeled snapshot format only published, stepped and inspected a one-peer bus; another labeled restore atomicity used from_snapshot without in-place restore. The oracle checked input-domain and expected-output agreement, not the semantic strength of these labels.

Study API estimate: $1.563717 from 24 physical requests. The cumulative accounted total is $25.504689 under the unchanged $40 cap, leaving $14.495311. No unsettled reservations or pending promotions remain. The study’s $12 reservation-inclusive ceiling and $6 target were not exhausted. Its conservative peak commitment was $7.005904, higher than final usage because in-flight requests reserve worst-case context.

API figures are conservative token estimates, not invoices. They exclude local compute, fixture/oracle development and engineering work. The two policies share the same stronger builder/reviewer profiles; the assisted policy adds cheap scout calls and evidence, so this is not equal compute.

What to do with this result

Keep the stronger maintainer and explicit completion gates as the default for the next practical task. Use additional workers selectively for concrete verification gaps, then measure whether their evidence changes an otherwise incorrect outcome. Before increasing swarm size, test longer, interacting maintenance issues across several independent repositories with the same reviewer and a meaningful same-evidence control. Add a preregistered bank of known faults to measure which additional tests detect defects missed by the common evidence. That is a proposed next experiment, not additional testing performed here.

This pilot establishes an executable, auditable maintenance comparison. It does not establish production robustness, general model rankings, or a gossip quality benefit. The earlier cohort exposed failures that this smaller module task did not; success on one smaller slice does not erase them.

Under strict acceptance, a successful project beats an unsuccessful one; two failures draw. Under coverage, more fully passed requirement groups wins within the same application. There is no cost or speed tie-breaker. Win score counts a win as one and a draw as one-half, with equal application weight.

A numerical Elo-like rating would add a scale without adding evidence here. Starting ratings, update order, and tuning choices would obscure the two-project sample. We therefore show separate observed ranks and explicit W/D/L. The analysis retains six same-repetition-index comparisons as a sensitivity check, but repetition numbers do not create shared seeds or a preregistered paired statistical design.

What a future rating system would require

A useful broader ranking would need more independent repositories and task families, clear opponent/task sampling, predeclared outcomes and budgets, uncertainty estimates, and checks that rank changes reflect new evidence rather than arbitrary update order. Batch pairwise models are available, but fitting one does not compensate for missing task diversity. The approach follows the distinction between descriptive win matrices and uncertainty-aware ranking in Chatbot Arena’s methodology; Elo Uncovered discusses sensitivity in Elo-based NLP evaluation.

Elapsed time is a diagnostic, not a speed trophy

The retained clock is controller time.monotonic, starting before supervision and ending after final evaluation. It includes model work, Git, Docker, the deliberate process kill/recovery, and final public/private validation. It excludes study preflight and later audit/diagnostics.

Shared-host contention varies, and concurrent calls overlap. These medians do not establish causal speedups. A fast failure is still a failure. Accepted-only time describes the successful subset and cannot be compared to zero-success arms as if their time were zero.

Historical provider-request latency is unavailable. The 289 journals lack request end timestamps or durations; trace starts, file modification times, and nearby validation events cannot replace them. The report leaves that metric unavailable rather than estimating it from unrelated timestamps.

The original no-op eligibility bug and three bounded portfolio stops remain part of these measured outcomes. Comparison metrics do not repair, rescore, or erase that limitation. The detailed frozen study distinguishes audit-format errors from state-policy failures and shows the earlier-stage passing source that became ineligible.

The executed scope was a maintenance slice of this repository’s existing gossip_harness/transport.py. Both policies use the same stronger coding maintainer and stronger reviewer. The assisted policy adds two cheap, independent test scouts per stage; scouts propose tests, not competing full implementations.

A new versioned controller preserves previously valid retained source when a later proposal is invalid or makes no effective change. After two stagnant reviews it can escalate, with at most two escalations; it never automatically accepts on stagnation. Both policies retain six review calls, four repair calls, explicit acceptance and empty outstanding requirements. The prior experiment’s CORE, evidence, outcomes and review artifact remain frozen. Scouts work independently from the same stage-start source, contract and public evidence. Each proposes up to four data-only tests; at most eight new scout tests are admitted per stage.
