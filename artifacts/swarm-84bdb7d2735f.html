The stronger next hypothesis is that several inexpensive implementations can supply useful diversity, and a capable reviewer can expose the differences that matter. This is worth testing. Its value depends on finding correct candidates and selecting them at a competitive total cost.

Recommendation: start with four independent candidates. Compare fixed tests and fuzzing against a stronger reviewer’s discriminating tests on the same candidate pool. Keep a strong single-worker baseline and a cheap worker with sequential repair. Measure selected correctness, not how many agents agreed.

Research and proposed experiment design only. No candidate-swarm implementation or paid swarm trial has run. The current discovery/recovery studies are separate experiments; their findings do not substitute for this evaluation.

The idea has close precedents

Fujitsu’s April 8, 2026 report is the closest match. Eight Qwen3.5-27B attempts supply patches and tests; tests run across candidates and a weighted pass-rate selects one. The authors report 374/500 (74.8%) on SWE-bench Verified. Many harness changes contribute, and cross-system comparisons lack uniform measurement. This does not establish that the smaller-model system is cheaper than a stronger single worker, or isolate the causal gain from selection. Fujitsu author report.

ByteDance reports a useful failure mode. Its plain patch selector peaked around five or six candidates, then worsened at eight or nine while the pool’s achievable coverage kept rising. Its later system added execution, deduplication, and tool-assisted selection. More candidates can therefore expose a selection bottleneck; they do not ensure a better final submission. Trae author report, May 2025.

These sources support trying candidate generation plus verification. They cover different tasks, models, budgets, and evaluators; their headline results are not a forecast for this harness.

Two bottlenecks, two different remedies

No correct candidate

A selector cannot recover a solution that no worker produced. Improve the generator, context, or repair budget.

A correct candidate is missed

Improve the test evidence and selection rule before buying more samples.

Correct selection costs too much

Reduce redundant attempts and reviewer work, or prefer the stronger single-worker baseline.

Independence matters because early agreement can collapse the pool into copies of the same mistake. Each worker should begin from the same frozen base with its own context and private implementation. Different personas do not prove independent errors; measure behavioral diversity and failure overlap.

The reviewer’s most useful output may be a precise counterexample: “these candidates disagree on this valid input; the contract requires this result.” A long explanation or confident vote is weaker evidence. A stronger model can still invent an incorrect expectation, so the execution result and the validity of the test must remain separate records.

Gossip is compatible with this design, but it is not what makes selection work. A simple coordinator and immutable artifact store are enough for the first study. Replaying identical candidate and test artifacts over broker or gossip transport can later isolate resilience and delivery cost.

  1. Bind the task. Freeze the complete specification, initial Git tree, public tests, model settings, budgets, and final holdout before generation. Each candidate uses a separate repository and bounded file scope.
  2. Generate four attempts. Use the same inexpensive model first. Keep implementations private until submission. Require immutable candidate commits and bounded test suggestions with contract references.
  3. Create independent tests. Freeze the same union of eligible candidate-authored tests, a candidate-blind specification batch, public tests, and bounded fuzz cases for both pool-selection arms. A stronger reviewer may then inspect anonymized diffs and this common execution evidence and add only its bounded minimal distinguishing tests.
  4. Validate and execute. Accept tests through a restricted data schema. Record invalid labels, bad setup, candidate exceptions, timeouts, and assertion failures separately. Run each eligible test against every candidate; deduplicate equivalent tests.
  5. Select deterministically. Apply mandatory regression gates, a frozen coverage/behavior ranking, and a declared tie rule. The reviewer produces evidence and can abstain; it does not silently change the acceptance contract.
  6. Freeze and evaluate. Record the selected candidate before opening holdout results. Evaluate all frozen candidates afterward to measure the pool’s available correctness, without feeding those outcomes back into this task’s selection.
  7. Promote the exact tree. Accept one complete tested commit. Code splicing creates a new candidate and would require a separately counted repair phase and complete revalidation.

Candidate, test, and receipt manifests should bind the base tree, contract version, content hash, origin, and relevant execution settings. A message saying “passed” must resolve to an executor receipt. A quorum of model opinions is not an acceptance gate.

Discrimination is useful only after validity

A test that divides four candidates into two equal groups has high discriminatory power. It can still be wrong. Start by establishing what the specification supports, then ask how much new information the test supplies. Fifty copies of the same assertion should not outweigh one valid counterexample.

Useful task-specific probes include duration parsing boundaries, quoted CSV newlines, mixed dependency schemas, and disconnected cycles. Metamorphic checks can change titles while preserving counts or consistently rename all IDs while preserving graph structure. Preconditions matter: changing input order may legitimately change ordered ID lists.

For the first mechanical validation, use tasks with an authoritative reference to reject incorrectly labelled proposed tests. Label that condition oracle-assisted selection. A separate deployable condition must rely on public preserved behavior, grounded assertions, valid metamorphic properties, and abstention. A model agreeing with another model does not turn an ambiguous requirement into ground truth.

The proposed comparison

Start with eight new tasks across at least three small projects, two repetitions each. This is an exploratory pilot, not broad evidence of software capability. Freeze the roster before sampling; include enough failures to distinguish the strategies without tuning the tasks to favor one.

Match reviewer-generated test count and execution allowance against a deterministic fuzz control, so extra tests alone do not masquerade as reviewer value. Use paired comparisons and common dollar ceilings; also report outcomes under a common time ceiling. Equal caps do not imply equal spend: compare observed correctness–cost–latency tradeoffs. Charge every failed candidate, repair, reviewer request, and test execution. Record actual API charges once, while allocating reused candidate-generation costs to each comparison arm. The shared pool is not free just because it was generated for another arm.

As a diagnostic, give the strong single baseline the same useful public test evidence and charge it the allocated cost of producing that evidence. This separates a benefit from better tests from a benefit from having more workers. Predeclare nested candidate subsets of one, two, and four; expand to eight only if the initial pool and selector justify it. Choose model snapshots and limits before the pilot, not after inspecting which combination wins.

Keep per-task outcomes visible and report uncertainty at the task level. Repeating one tiny fixture many times does not create many independent projects. A rising pass@4 with flat or falling selected success is a verification problem, not a reason to advertise the oracle score.

The current harness needs a stronger evaluation boundary

Current studies are cooperative evaluations. Their Docker checks are mounted inside the candidate container, and repair feedback reveals parts of the checks. They are useful acceptance gates, but they are not an adversarially sealed holdout. Their visible failure feedback cannot later be treated as hidden evaluation.

Before a selector study, split public feedback from final evaluation. Keep hidden expected outputs and evaluator logic on the host side, outside candidate repositories and containers. Send bounded inputs through a data-only interface and compare returned values in the trusted evaluator. Resource limits, schema validation, and separate output channels are part of the boundary; a container alone does not seal the oracle.

Freeze selection before final evaluation. A reference implementation used to validate generated test labels gives the system privileged help and must remain a separately named experimental condition. Success there tests candidate and selector mechanics; it does not prove that production reviewers can resolve ambiguous specifications without a reference answer.

Shared model errors, weak coverage, correlated samples, reviewer bias, and small task counts remain even after those engineering changes. Bigger candidate pools also increase reviewer context and execution cost. None of these limitations is cured by peer-to-peer dissemination.

When to continue—and when to stop

Continue if selected correctness improves at a comparable total dollar or latency budget without an unacceptable false-acceptance rate. Require the stronger-reviewer arm to improve over fixed selection on the identical pool; otherwise its added complexity has not earned its cost.

Change direction if extra candidates mostly duplicate the same error. Spend on a stronger generator or a discriminating test. If correct candidates already exist but selection misses them, improve verification first. If a strong single worker matches the result more cheaply, use it.

This is a credible next experiment with a practical stopping rule. It tests independent search plus evidence-based selection. Gossip can remain a transport option for the resulting immutable artifacts, with its own resilience and communication-cost comparison.
