Does diversity produce
better finished work?

This benchmark compared four sequential cheap-agent revisions with four independent cheap-agent branches. The certified primary results favor independent branches on requirement coverage, but only two of ten trajectories met the full completion contract. The audited fault bank and selection tests found no additional measured benefit from scout evidence beyond the reviewer’s tests.

A local coverage advantage, with weak completion and test contribution. Independent branches accepted one of four projects, compared with zero of four serial chains; equal-project requirement coverage was 90.3% versus 75.3%. The contextual strong anchor accepted one of two. All ten trajectories and accounting passed the independent primary audit. All 103 candidate/fault executions passed their separate audit. Generated evidence did not improve the counterfactual selectors’ measured quality over public cases alone. The 420-case transport replay found scenario-dependent tradeoffs, not a universal gossip advantage.

A control that separates breadth from repeated work

Both primary policies get four cheap-model initial call opportunities per stage. The serial policy passes each preceding retained implementation and executed public/prior-stage evidence to the next builder, preserving all checkpoints. The independent policy gives every builder the same stage-start source without peer outputs. Both use the same stronger reviewer and bounded repair/escalation rules. Matching opportunities does not make actual token usage or evidence identical.

Scouts run only after the initial pool freezes. They see the stage-start source, cumulative public contract and public cases—not candidate implementations, peer probes, private cases or the fault bank. Their admitted data-only tests then run against every candidate. This permits measurement of current-stage test contribution separately from prevention during initial generation. Prior-stage admitted tests remain regression evidence.

Per stage, the common controller allows at most four reviews, two repairs, eight new reviewer probes and one stall escalation after two stagnant reviews. Each of two scouts may propose four cases. A trusted oracle rejects invalid input or incorrect expected answers without correcting them. Unknown provider outcomes halt globally without automatic retries. Candidate code runs only inside the pinned Docker validator.

Agent-interface limitation. Live roles make bounded structured JSON proposals and reviews, with no autonomous shell or tool loop. The controller executes tests and returns evidence. A proposed probe must supply complete literal expected JSON, including exact digest strings when present; the trusted oracle rejects wrong expectations without repairing them. These results describe this interface, not all fully tool-enabled coding agents. How much these constraints contributed to failures was not measured, and wrong expectations cannot all be attributed to hashes.

Freeze and scoring boundaries

Trusted golden implementations, semantic mutants and correct controls may execute during qualification. No model-generated private, cross-policy or fault diagnostic runs until all ten provider-driven trajectories, candidate sources, proposals and final selections are frozen. The independent audit then checks retained sources, receipts, roster, journal, accounting, timing and Git identities. Censored or unexecuted work remains explicit; a budget-limited partial cohort cannot masquerade as a completed comparison.

Why visible completion was not enough

Calendar serial repetition 1 and independent repetition 1 completed both visible milestones and passed all 30 new-feature private scenarios. They still failed final acceptance: 75/78 and 76/78 total private scenarios passed, respectively. Both regressed inherited malformed-input handling: a nested list/dict operation produced internal instead of the required invalid error. The serial output also dereferenced malformed top-level commands before validation.

These failures are typed-validation regressions, not evidence of failed atomic rollback or corrupt state. Both runs scored 12/13 contract groups, but that is not 12/13 uniformly sampled functionality: the single baseline group contains 48 private scenarios; seven exchange groups contain 14 and five settlement groups contain 16. Passing the tested new-feature scenarios does not prove every new-feature interaction correct.

This is source-bound, post hoc interpretation of already executed selected-source receipts. No new candidates or private tests ran for the memo. Unexecuted static follow-up ideas remain separate and do not change scores.

Graph: unreached work and stalled completion are different failures

All five graph finals preserved all 48 measured legacy private scenarios and 16 legacy groups. Three runs stopped during rename, so their failing patch scenarios are unreached scope, not regressions in an attempted patch implementation. Final coverage intentionally includes that unfinished work.

Independent repetition 0 passed all 75 private scenarios, 29 contract groups, 32 fixed public cases and 43 active public/probe checks. It still completed only one milestone: all four final-stage reviewer decisions were inspect, and the last retained an unresolved provenance requirement. A bounded escalation had already occurred and one repair slot remained unused. This is a completion-control bottleneck on the tested contract, not an accepted release; no extra continuation was tried.

The graph strong anchor passed 74/75 private scenarios. Its remove-and-recreate provenance defect was also exposed by three generated probes, yet every review remained inspect and neither repair slot was used. Source inspection suggests underallocated origin tokens, but the receipt reported only an error; a particular exception or successful one-fix rescue was not measured.

Failure labels alone do not establish cache corruption, broken atomicity or failed retries: some graph scenarios failed because invalidation arrays or audit IDs were wrong while other recorded behavior was correct. These are independently reviewed, source-bound interpretations of selected outputs only; unselected candidates are left to the diagnostic matrix.

Continuations did not reliably improve the same evidence

The six bounded stops were not all equivalent. Five selected sources still failed active cases; one passed all active cases but did not satisfy explicit controller completion within the fixed review limit. Three stops retained unused repair capacity because the review ceiling was already binding. Extra continuation was not executed, so these are controller bottleneck observations, not demonstrated rescues.

For eleven repairs compared on exactly the same cases supplied to that repair request, four reduced the failure count, four increased it and three left it unchanged. Five introduced at least one failure on a previously passing case. Exact source changes and newly admitted passing tests can reset stagnation despite unresolved behavior; novelty alone is not reliable forward progress.

The secondary diagnostics below separate generated quality, fault sensitivity and selection. They do not causally explain every primary difference. The centrally instrumented coding contrast does not isolate gossip.

Do the tests detect the defects that matter?

The semantic fault bank and correct controls are fixed before live calls. Qualification checks golden/control correctness, each mutant’s public-test survival and an independent witness failure. Workers never see the faults, witnesses or fault scores. The key diagnostic is detection of distinct public-surviving fault families, alongside correct-control rejection and repeated coverage.

Scouts added no detected family beyond reviewers in these four banks. The combined evidence missed most calendar families and detected about half of graph families. These are sensitivities to the frozen bank, not counts of real defects repaired.

No measured selector gain from the extra evidence

Initial and final eligible pools are analyzed separately. Exact source hashes deduplicate execution within a stage and purpose while checkpoint occurrences remain distinct. Repaired final selections can lie outside an initial pool, making same-pool regret undefined.

All eight counterfactual evidence configurations produced the same measured quality and abstention outcomes. Each made 26 selections and eight abstentions over 34 initial/final pool observations. Public-only, scout, reviewer and combined evidence tied within every pool, in both own-history and pooled same-project/stage scopes. Two calendar stage runs switched candidate identity in four initial/final pool observations, removing one additional admitted-probe failure without held-out quality gain. The claim is equal measured private quality, not identical winners.

Test continuation control before adding agents

Recommendation only: a prospective twelve-trajectory pilot on two genuinely new application domains, two repetitions and two cumulative milestones. This is not an implemented, scheduled or newly authorized paid study. The current results describe bottlenecks; they do not prove these changes will fix them.

ArmControllerInitial formationContrast
ACurrent frozen controllerFour independent cheap candidatesContinuation baseline
BFailure/uncertainty routing plus repair-checkpoint retentionFour independent cheap candidatesB vs A: controller package
CSame improved controller as BFour cheap serial revisions, retained checkpointsB vs C: candidate formation

The proposed controller would route observed failures to an eligible alternative or targeted repair while preserving a later review opportunity. When executed evidence passes but uncertainty remains, it would demand a focused admissible probe or an explicit unresolved stop. It would retain pre-repair and repaired source checkpoints and compare them on identical cases, recording every regression. Source changes or extra passing tests alone would not count as progress on an unresolved known failure.

The offered ceilings stay fixed: four reviewer calls, two repairs and at most one strong escalation within those repairs per milestone, with the same models, probe admission and acceptance gates. Explicit review acceptance, source eligibility, execution gates and final independent checks remain necessary. More useful repairs may still mean more realized compute; checkpoint retention adds evaluation work and changes the selector’s pool, so any improvement belongs to the whole controller package.

Pairing and a decision rule before spending

For A/B, generate one fresh first-milestone independent pool per project/repetition block, freeze it and candidate-blind scout evidence, then branch the controllers with separate review/repair calls. C forms a fresh serial chain from the same trusted baseline. Later accepted lineages diverge naturally; never replay responses into changed requests. Count shared setup once in physical spend but attribute equal offered setup to each relevant comparison. This reduces one source of variance without creating independent end-to-end replication.

Advance only if B improves independently accepted whole projects in both domains, without losing paired full acceptances, inherited-contract preservation or valid acceptance gates; apply the same rule to B versus C before expanding candidate breadth. More tests, fewer stops or partial coverage alone would not justify scale-up. Ties or a gain confined to one domain call for broader evidence, not a general claim. Four blocks across two domains remain an exploratory pilot, with no calibrated Elo.

Keep alternative test formats as a separate later experiment so they do not confound controller and formation. No new strong anchor or larger pool is needed for these two contrasts.
