Make completion
mean more.

We tested sustained maintenance with stronger review, generated probes, real process kills, and independent Git updates. The durable machinery worked at the tested boundaries. More inexpensive builders did not produce better completed software in this study.

18 trajectories finished and independently audited. A stronger builder with a stronger reviewer completed the full acceptance contract in 3/6 runs. One cheap builder and four cheap builders, each with that same reviewer protocol, finished at 0/6. This supports a stronger maintainer as the current default, not a larger homogeneous swarm. It is a small, synthetic comparison with a material harness eligibility bug and different generated evidence across policies.

The previous study passed every visible milestone, yet later contract probes found failures in all portfolio outputs. This round tested stricter verification and the missing one-cheap-builder-plus-reviewer control. The three bounded portfolio stops had different causes

  1. A harness eligibility bug plus reviewer persistence in an incorrect objection. A no-op repair retained previously valid source bytes but marked them invalid. The reviewer also continued an ordering objection after the code had changed and never requested acceptance.
  2. Inspection without progress. Another buildgraph run used all six reviews on inspection, requested no repairs, and exhausted its probe allowance. Its retained milestone-one source passed all 12 corresponding private cases, yet the controller never received an acceptable completion decision.
  3. Unresolved tested behavior. The early calendar run exhausted six reviews and four repairs with active failures still present. Its attempted-scope private outputs also showed refused held cancellation, an allowed held move, and an extra confirmation field; future milestone-four failures are unimplemented scope, not separate completed-feature defects.

The no-op bug materially limits model-only conclusions. The frozen engine conflated proposal admissibility with retained-source validity. Two such demotions occurred across 67 attempted stages; one cheap run recovered with a later valid proposal. In the bounded buildgraph portfolio run, a preplanned post-freeze diagnostic tested the demoted source against all first-three-milestone private checks: 36/36 cases, 12/12 requirements passed. The final retained alternative passed 27/36 cases and 8/12 requirements.

A suite-passing earlier-stage source was available. That does not demonstrate whole-project success: milestone four was never attempted and the reviewer never requested acceptance. Another candidate’s earlier scope-invalid proposal is a separate event. Primary scores and CORE remain frozen; this issue calls for a versioned harness fix, not a retroactive score adjustment.

Each review may propose up to four data-only probes, with at most eight newly admitted probes per milestone. The trusted host reference checks the proposed expected output exactly, including JSON types. Wrong expectations are rejected without supplying a corrected answer. No generated executable test code runs, and private cases are not consulted to validate a proposal.

Admitted probes run against every current candidate and carry into later milestones unless an explicit contract change retires them. A reviewer’s acceptance remains provisional until the exact immutable selected source passes the cumulative public and admitted-generated gates.

The policies do not receive identical generated evidence. Reviewers can inspect candidate code when choosing probes. That makes discoveries depend on the implementations available to each policy, even under identical proposal ceilings. Final private suites are shared across policies; the probe sets may differ.

Probe failures are counted as failed candidate-by-probe observations, not distinct bugs. A discriminating probe produces mixed outcomes within a candidate pool; that metric is structurally zero for a single-candidate policy. It cannot by itself rank the quality of singleton verification. Final quality, repaired behavior, and observed exposure need their own denominators.

Across 378 proposal attempts, 314 were admitted and 64 rejected: 49 had wrong expected answers, six had oracle-rejected inputs, one duplicated an existing case, and eight exceeded the stage allowance. This shows why independent label validation mattered. Neither admitted-test volume nor 39 discriminating portfolio probes produced an accepted portfolio project in this run.

The host reference is an oracle-assisted benchmark advantage. It can validate a proposed label because the experiment has a trusted implementation; arbitrary production requirements often do not. Test validity, discriminating signal, useful repairs, final requirement coverage, and whole-project acceptance must therefore be reported separately.

A real process death at a precise boundary

For each trajectory reaching milestone two, the supervisor sends SIGKILL after its first reviewer response is durably saved but before accounting settlement. No other model request is in flight. A new process must replay the saved work, preserve one settled charge for that response, and continue the project without redispatching it.

This is stronger than the previous clean exit between milestones, but its boundary is deliberately narrow. A dispatched request with no durably saved response has an ambiguous outcome and cannot be automatically retried. The study does not claim recovery from every in-flight API failure or arbitrary distributed crash.

All 17 trajectories that reached the kill point resumed in a new process. The one earlier stop never reached that boundary. This verifies a specific retained-response recovery mechanism; it does not establish provider-side exactly-once semantics.

Stateless patch agents still depend on the controller’s durable journal, exact source bindings, explicit completion state, and repair limits. A process restarting successfully is not sufficient evidence that project direction or accounting survived; those must be checked.

Incoming work must invalidate stale evidence

Before milestone four, the controller merges a trusted policy change from an independent Git history into the maintained application. A prepared receipt tied to the prior accepted head must be rejected. Models then adapt their backend to the merged policy while preserving earlier requirements.

Supplementary result: 30/30 same-database stories passed

After all live calls ended, selected milestone-one through milestone-four sources operated on the same database created by their own first implementation. Two targeted stories per application used at most 16 commands each. Every one of the 15 eligible trajectories passed both stories: 30/30 stories and 465/465 exact command-step comparisons. Three early stops lacked all four versions and were skipped.

The cases exercised source/policy continuity and unambiguous grandfathering. Buildgraph historical-counter continuity is an additional operational assumption, not a retroactive primary requirement. Twelve eligible trajectories that failed primary acceptance also passed these stories; compatibility does not erase their other failures. Arbitrary historical schemas, concurrency, interrupted migrations, and every operation sequence remain untested.

The adapter and cases passed 19 focused checks plus independent review. Matching golden Docker qualification passed all four trusted stories before candidate evaluation. The completed diagnostic used no API calls, changed no primary scores, and supplied no model feedback. A first attempt interrupted by Docker socket access before scoring is retained separately from the successful second attempt.

The live policy integration is not a claim that agents autonomously solve arbitrary textual merge conflicts. This round also does not compare gossip transport with orchestration.

Build around a stronger maintainer

Use a stronger builder with explicit durable requirements and independent verification as the current default. Add cheap workers selectively for alternative implementations, focused investigations, and adversarial test proposals. This study does not justify scaling a homogeneous implementation swarm.

Before the next live comparison, version and test the retained-source/no-op fix and a reviewer progress rule: an exhausted inspection loop needs a concrete decision or explicit blocked state. Preserve good source when a proposed edit is rejected. Broaden interaction coverage—especially identity lifetime, held-state rules, policy limits, malformed input combinations, and audit contracts—without treating generated confidence as proof.

The next useful validation is a real repository with several interacting issues and continued maintenance, keeping the same stronger maintainer and comparing targeted assistance. A trusted benchmark oracle will usually be unavailable, so production verification must expose uncertainty instead of silently assuming correct test labels. A gossip-driven software-quality advantage remains untested. Reliable dissemination and Linux-style delegated integration are compatible with this architecture, but these quality experiments do not isolate a transport benefit.
