Carry the project
forward.

This study asks whether the system finishes a cumulative software project at the required quality bar, preserves earlier behavior, and resumes with its direction intact. It moves from isolated functions to two SQLite-backed applications, each developed through three interacting milestones.

The system carried every project through three milestones and a real controller restart. The portfolio passed the primary gate in 4/4 runs; both single-worker policies passed 3/4. But all four portfolio outputs failed at least one later source-informed contract probe. This supports the persistence mechanism and a narrow primary-score advantage—not a claim of robustly better software. Independent evidence audits and both supplemental analyses are complete.

These are bounded synthetic applications with real multi-file source, SQLite storage, fresh CLI processes, Git retention, and Docker evaluation. They are not sampled production repositories, an unrestricted tool-using agent, or a new test of gossip transport.

The controller introduces milestone requirements in order; it does not ask agents to discover the project roadmap. Milestones extend the same accepted source tree. Every model request contains the cumulative specification and visible cases for the current milestone, the current repository, prior notes, and machine-check history. Each stage adds eight visible scenarios and ten private scenarios. Final evaluation therefore has 24 cumulative visible and 30 cumulative private scenarios per project.

Two applications × three policies × two repetitions yield 12 live project trajectories, with up to 36 milestones. This is two application identities, not 12 independent projects. The contract is frozen in sustained-study-plan.json.

It may select and request repairs but cannot edit trusted tests, execute tools, or splice candidate implementations. There is no generated-test label oracle in this selection loop.

This is a bundled policy comparison. The reviewed portfolio changes candidate breadth, reviewer strength, total available calls, and cross-candidate evidence together. It cannot separately identify which factor causes an outcome difference. Both baselines now receive cumulative feedback and a continuation mechanism; actual feedback-continuation counts still matter more than their permitted maxima.

Workers return source patches plus strict control data: continue or complete, useful notes, and outstanding requirement IDs. A completion claim does not bypass the cumulative visible gate. Invalid controls, unauthorized paths, remaining work, failed checks, and repeated failures remain in the trajectory and can drive another bounded attempt.

The raw repairs counter means feedback continuations. It includes fixes to control records and requests that merely acknowledge completion, as well as source-code corrections. It must not be read as a count of semantic bugs repaired.

The controller records each proposal as immutable Git content before evaluating it. Notes and machine history accompany later requests. It counts lost previously passing visible cases as regressions, repeated unchanged source or failure sets as stagnation, and denied completion claims separately. These are observable proxies for retained direction, not a complete measure of reasoning quality.

After milestone 2, all requests and publication intents must be settled. The controller atomically saves and hashes its checkpoint, exits, and a new process verifies the contract, different PID, completed-stage count and status, exact Git head/files, and settled ledger before starting milestone 3.

The restart is scheduled at a clean boundary. It does not test a crash during a provider call, an ambiguous billing result, concurrent database clients, or an interrupted database commit. Application-level persistence is tested separately by fresh CLI processes sharing a SQLite file. Neither mechanism should be described as arbitrary fault recovery.

Prior checkpoint notes can mention an earlier candidate slot, even though a new milestone starts four fresh calls. That creates a possible label-carryover bias to investigate; a repeated label alone is not evidence of anchoring, particularly when the chosen source is also the best visible candidate.

The workers are stateless patch calls. Sustained behavior comes from the controller’s durable state, bounded loops, and explicit continuation protocol. If an attempt ceiling is reached, the trajectory is retained as incomplete; an unfinished earlier milestone cannot be skipped. Unknown provider usage and invalid infrastructure receipts stop the run for investigation rather than being converted into model repair feedback.

The quality bar comes before the cost comparison

Requirement coverageA group passes only if every associated final private scenario passes: 12 groups for the queue, 15 for inventory.

Continuity evidenceVerified new-process resume, retained requirements, regressions, denied completion claims, stagnation, feedback continuations, and terminal incompleteness.

Final private evaluation begins only after all provider work for that project trajectory has ended and the trajectory has been frozen. Private expected outputs and reference implementation material do not enter worker or reviewer context. The same host-side evaluator checks returned outputs against expected results; candidate claims are not acceptance evidence.

Historical milestone commits are also scored privately after the complete trajectory is frozen. Those retrospective scores are diagnostic only. A defect in an earlier milestone may be fixed later without permanently failing the project, provided the final source satisfies every cumulative requirement. Private failures are never fed back to the models within this comparison.

Supplemental post-hoc diagnosis: after all live calls end, evaluate the latest retained candidate in each portfolio slot at each reached milestone against that milestone’s frozen private suite. Reuse matching selected-source receipts and test other source versions locally. This separates a pool with no fully acceptable implementation from a selection miss when a better candidate exists. It does not change any winner or send private feedback to a model; repaired slots are not four untouched independent samples. Intermediate diagnostic results are kept separate from final-project quality.

Raw proposal-regression counts have different exposure in a four-candidate portfolio and a single-worker trajectory. Report those counts with their proposal/evaluation exposure, and analyze the selected milestone history separately. Neither a larger raw count nor fewer logged events alone establishes better retained direction.

Requirement coverage differs from raw test percentage: if any private scenario for a requirement fails, that requirement group fails. Acceptance is still bounded by the specified contracts and tests. Passing them does not establish production readiness, maintainability, security, or correctness for every possible workload.

Private expectations remain on the host, and individual evaluation cases use fresh processes inside constrained Docker containers. The execution boundary is not an adversarial VM guarantee; processes within a candidate evaluation share container state. No broader isolation claim is needed for the cooperative experiment.

The two retained primary failures

Strong single, workflow repetition 1: the invalid second command of a batch returns {"error":"invalid"} rather than the required {"at":1,"error":"invalid"}. It passes 29/30 private scenarios and 11/12 requirement groups. The empty-list observation confirms rollback in this scenario; this is an error-index violation, not demonstrated state corruption.

Cheap sequential, workflow repetition 1: claim-priority and legacy-restart-retry fail, leaving 10/12 requirement groups passing. The unambiguous claim-priority failure already appears when the frozen milestone-2 source is scored retrospectively: it chooses a lower-priority pending job instead of a higher-priority job whose lease has just expired. The audit-event failure needs a specification caveat: the prose says “FIRST successful finish” without explicitly stating per job-and-token. Receipt semantics suggest per-token behavior, which the private expectation uses, but the wording is ambiguous. That primary score is preserved; even without this case, the separate claim-priority failure keeps this project unaccepted.

The selector found a passing option—on the frozen suite

The post-hoc pool analysis evaluated the latest retained proposal in each of four slots at every portfolio milestone: 12 stage pools across four trajectories. Each pool contained an eligible implementation passing its cumulative private suite, and every selected implementation passed: 12/12 coverage, 12/12 selected correctness, and zero observed selection regret. Final-stage pools separately scored 4/4 on those measures.

It used 36 fresh local Docker validations and 12 reused retrospective historical receipts, with no API calls. At milestone 3, those historical receipts are separate from the primary final-acceptance execution. Latest slots include repairs; this is not a comparison of four untouched initial candidates. An alternative passing an earlier milestone was not carried through the rest of the project, so stage coverage is not counterfactual whole-project success.

These figures show that the selected candidates met this particular private suite. They do not cancel the later source-informed failures, isolate the reviewer's contribution, or establish that selection is trustworthy on unseen contracts. Some earlier visible ties also hid private differences; zero observed regret in four trajectories is a small-sample result.

A narrow post-hoc comparator: choosing the lexicographically first visible-eligible latest slot would pass the private suite in 11/12 stage pools, versus 12/12 for the actual reviewer. Four choices differ, but only one changes private correctness: in workflow portfolio repetition 0, milestone 1, candidate c0 fails self-dependency while selected c2 passes. All four final-stage pools contain exactly one eligible candidate after the reviewer-directed repairs. This is descriptive evidence from the already altered pools, not an independent run, an equal-opportunity causal control, or a whole-project result.

Build stronger verification before increasing the swarm

The useful result is a persistence mechanism and an evaluation lesson. The controller completed every planned milestone and clean process handoff, blocked false completion claims, and supported repairs that recovered badly regressed source. The portfolio's 4/4 primary outcome is encouraging for this bundled policy, but all four outputs still contain contract failures exposed by later probes. That is insufficient evidence to make a larger swarm the default route to higher-quality work.

For a quality-first next phase, keep the durable controller and require an independent verification loop before declaring a project finished. Clarify ambiguous contract clauses, turn reviewers' concrete concerns into executable checks, test malformed types and interacting operation sequences, and check atomicity, idempotency, migration, and failure recovery explicitly. Give each policy the same newly visible feedback and opportunities to repair. Then evaluate on a fresh final suite and broader repository changes.

Include three explicit controls: a stronger single worker, one cheap builder plus the same strong reviewer, and four cheap builders plus that same strong reviewer. Keep the adaptive feedback and completion rules aligned; the one-versus-four cheap-builder comparison isolates candidate count more directly from reviewer quality. Only add candidates when there is measured evidence of a coverage gap that another implementation can fill. Keep reviewer judgment distinct from observed execution, and measure whether extra work removes specification failures—not just whether another round produces code.

This next phase is a recommendation, not an executed study or a promised production guarantee. The current result compares two low-reasoning model profiles on two synthetic applications, with two repetitions per policy. It neither proves general policy superiority nor tests a causal benefit from gossip.
