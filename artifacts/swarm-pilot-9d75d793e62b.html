Gossip × Agents / candidate-swarm pilot / September 30, 2026

Four candidates.
One measured choice.

The proposed candidate-selection experiment is implemented. It compares independent inexpensive implementations and shared tests with a stronger reviewer, a stronger single worker, and a cheap baseline with bounded public-feedback repair. The offline proof and all 16 live task-runs are complete. The stronger single worker matched every pool policy’s acceptance at lower API cost.

The harness worked; this pilot does not justify adding a reviewer swarm. Strong single and all three pool selections passed 16/16 task-runs; the cheap public-feedback baseline passed 14/16. The reviewer changed no winner. A separate post-hoc audit found that public gating plus the already-frozen candidate order selected the same winner in every case, so even the pooled tests’ incremental selection benefit is unproven here.

These are small Python function tasks, not eight real software projects. Generated test labels receive privileged reference-oracle validation. No gossip transport comparison or autonomous repository tool-use loop is included.

The inexpensive model is gpt-5.4-mini-2026-03-17; the stronger baseline and reviewer use gpt-5.4-2026-03-05. Both use low reasoning effort and a configured 4,096-token output limit. These are pinned model profiles, not a sweep over whichever configuration later wins.

All three pool policies reuse the same implementations. Their differences measure selection evidence, not independent coding samples. A strong baseline supplied with the pool’s test evidence remains explicitly deferred; cheap sequential repair given that same evidence is also needed before crediting a benefit specifically to four workers.   1. Validate proposed tests. Strictly parse bounded JSON records and require a known requirement ID. The host reference oracle checks the expected result. Incorrect labels are rejected, never silently corrected. No generated executable test code runs.
  2. Build the shared matrix. Deduplicate by input, preserve evidence provenance, and run every eligible baseline case against every candidate. Public cases are mandatory gates.
  3. Add matched evidence. Reviewer and fuzz controls receive the same proposal-slot budget and the same accepted extra-execution count. If sufficient unique fuzz cases are unavailable, reviewer extras are reduced to match.
  4. Choose deterministically. Among candidates passing public gates, rank the fraction of unique eligible cases passed. Break ties using a frozen anonymous order, independent of generation order. More duplicated tests cannot create extra votes.
  5. Freeze the choices. Persist every policy’s selected commit before evaluating any final cases. The final evaluator then scores all candidates to measure both selected success and the pool’s available correctness.
  6. Publish exact content. A passing choice must match the host-evaluated file hash at its exact Git checkout; promotion uses the existing ownership and publication fences. Fragments from different candidates are not combined.

A “distinguishing” reviewer test has a mixed pass/fail vector across the four candidates. That is a measured behavioral distinction, not proof of a useful new requirement. Validity, duplication, unique additions, and actual changes to the chosen candidate are separate metrics.

Predeclared nested subsets of one, two, and four candidates use prefixes of each frozen anonymous order. Their coverage measures whether any candidate passes public and final checks. These post-selection diagnostics do not retroactively change the primary winner.

A host-side evaluator, with explicit limits

Only candidate source, a generic transport adapter, and JSON inputs enter the container. Expected outputs and reference-oracle code stay on the host. Every case runs in a fresh Python process; the host compares returned JSON values with the expected type and value. A candidate’s own “passed” field or process exit code is never sufficient for acceptance.

Malformed output, extra JSON values, duplicate object members, non-finite numbers, exceptions, timeouts, and excessive output fail closed. The harness bounds input/output sizes and verifies process/container cleanup. Network access and candidate mounts follow the isolated Docker execution policy.

Oracle assistance remains a major limitation. A trusted reference filters generated expected outputs before selection. This tests candidate selection with privileged label validation; it does not prove that a production reviewer can decide ambiguous behavior without a reference answer. Even zero harmful selections would not establish reviewer trustworthiness when the host oracle screens its labels first.

Final evaluation is first invoked only after all choices are durably frozen. However, a generated or fuzzed visible input may coincidentally match a final-case input. The runner audits that overlap after selection and reports it; “withheld from the prompt” must not be confused with a guarantee of disjoint inputs.

Cases use fresh processes but share their candidate’s container and temporary filesystem. This is not a separate security boundary between cases, a VM-grade isolation claim, or an exhaustive adversarial evaluation. It improves on mounting expected-output checks alongside candidate code without erasing all execution risks.

Two observed failures and their selection evidence

A deletion rule missed by the cheap baseline

In repetition 1 of config-merge, this actual final-case input required removing a nested null while replacing an earlier scalar:

Input:    {"layers":[{"a":5},{"a":{"x":null,"z":0}}]}
Expected: {"a":{"z":0}}
Observed: {"a":{"x":null,"z":0}}

The cheap baseline cloned the replacement object without applying the contract’s nested deletion rule. Its public examples passed, so the available repair loop stopped. The stronger single worker and all four pool candidates passed the final checks for this task-run.

A useful pool, with existing fuzz evidence

In repetition 0 of config-expand, the cheap baseline and one pool candidate treated lowercase ${bad} as a reference. The contract permits only ASCII uppercase names, so that token should remain literal. Three prebuilt trusted fuzz inputs in the baseline matrix rejected the failing pool candidate; all pool selectors chose a passing implementation.

The selecting evidence in that case came from trusted fuzz, not candidate-authored or reviewer-generated tests. The post-hoc public-only rule chose the same winner, so these fuzz cases cannot be credited with causing the successful choice. This case also does not isolate four workers from giving those same checks to a cheaper repair baseline. The cheap baseline passed this task in the other repetition, illustrating sample variation.

Account for the whole portfolio

The pilot uses the existing cumulative ledger, starting from $0.325268 of earlier usage. The active hard cap remains $10; the user has authorized up to $50 additional budget if needed, but that is not a spending target.

The frozen per-policy reservation ceiling is $6 per task-run. The request-start cutoff is 900 seconds; it stops new calls after the allowance, rather than claiming a strict end-to-end latency bound. Each call reserves a full-context conservative bound before dispatch. Equal ceilings do not imply equal actual spending.

Physical usage accounting counts each candidate, candidate-blind test call, reviewer, and baseline request once. Comparative pool policies are each allocated the shared candidate/test-production costs; only the reviewer policy adds reviewer model usage. Reusing a pool does not make its generation free. The matched fuzz control’s extra-test count depends on the reviewer’s valid novel output, while its attributed cost excludes the reviewer call. That row is a paired test-content diagnostic; it is not the cost of an independently deployable fuzz policy. Container work and observed elapsed time are separate diagnostics; token charges do not represent total hardware or runtime cost.

128 actual provider requests accounted for $1.365116 in this study: 16 stronger baselines, 16 cheap baselines, 64 candidates, 16 candidate-blind test calls, and 16 stronger reviewers. The reviewer fees alone were $0.787867, with no changed winner.

Including all earlier studies, the cumulative estimate is $1.690384, leaving $8.309616 under the unchanged $10 hard cap. None of the additional authorized budget was needed. There are 165 cumulative paid provider requests; the 173 ledger reservations also include eight earlier zero-cost replays.

Fixed-pool API cost was 2.36× the stronger single worker’s cost; reviewer-pool cost was 7.38×. Both had the same observed acceptance as that baseline. The cheap baseline cost less and missed two outcomes. These are observed token-cost comparisons on this sample, not equal-spend quality estimates or invoice totals.

All 128 new reservations are settled. The shared ledger has zero unsettled reservations, zero pending publication intents, and 45 completed records, including this study’s 16. Recorded task-run durations sum to 1,826 seconds; 256 validation calls sum to 417 seconds of measured validation time. These local diagnostics do not establish production latency or total compute cost.

Keep the harness; raise the difficulty before scaling the swarm

A pool helps only if it produces correct candidates that a simpler baseline misses, and the selector can choose them economically. Higher candidate coverage without higher selected success means selection is the bottleneck. In this selection experiment, the reviewer earns its extra cost only if it improves choices against fixed selection and the matched fuzz control.

If all methods saturate, the tasks need to become more discriminating. If candidates share failures, improve generation or diversity. If correct candidates exist but are missed, improve verification. Prefer the simpler baseline until measured quality–cost tradeoffs justify a more complex policy.

Use the stronger single worker as the default supported by this pilot. It matched every pool policy at lower API cost. The reviewer’s distinguishing tests were real, but their marginal outcome benefit was zero. Even baseline pooled evidence did not alter the post-hoc public-only choices. Increasing reviewer volume on these fixtures would not answer the unresolved question.

The useful next experiment is a harder, newly frozen task set with genuine selection headroom: candidate disagreements that public examples do not resolve, spec-valid independent final cases, and matched single-worker/cheap-repair access to the same visible evidence. Predeclare a public-only pool selector and a reviewer-free fuzz policy whose test budget is fixed independently of reviewer output. Keep a fresh final evaluation set and measure both missed correct candidates and wrong-label risk without assuming a production reference oracle exists.

This completed pilot establishes a working measurement and publication mechanism. It does not establish real-repository productivity, cross-model diversity, gossip transport benefits, production reviewer trustworthiness, or population-level superiority. Eight related synthetic task identities and two repetitions are a calibration study.
